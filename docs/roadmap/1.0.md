# Roadmap to 1.0

## Status

- Status: active
- Last reviewed: 2026-07-31
- Scope: stable read-only IC reporting, follow-up collection, and caching
- Current overall coverage estimate: 55%

Coverage percentages are planning estimates, not protocol conformance scores.
Capabilities differ substantially in size and value, so endpoint counts alone
would give a misleading result. Update the estimates when a coherent reporting
capability is added, removed, or materially expanded.

## Product Direction

The goal is one user-facing tool and reusable library for querying the IC:

- one `icq` command hierarchy;
- typed text and JSON reports;
- explicit live, cache-only, refresh, refresh-missing, and refresh-stale
  behavior where caching is appropriate;
- stable identifiers that can drive typed follow-up queries;
- provenance that distinguishes Registry state, canister state, certified
  responses, official indexes and APIs, and external enrichment.

Internally, the tool retains one live adapter per authority family rather than
one universal IC adapter. The adapter and provenance rules are defined in
[IC Reporting Adapters](../design/ic-reporting-adapters.md).
The current command hierarchy and collection modes are summarized in
[CLI Usage](../cli-usage.md).

`ic-query` remains read-only. It is not intended to replace `dfx`, provide
arbitrary Candid invocation, or manage canisters, neurons, tokens, or network
configuration.

## Workstreams

### 1. Ledger and transaction evidence

- Keep typed ICRC index account-history queries aligned with the official
  index interface and preserve separate ledger, index, account, and endpoint
  provenance.
- Keep supported tip-certificate authentication, certified-data proofs, and
  required-leaf validation aligned with ICRC-3 and the IC interface.
- Preserve explicit archive follow-up, bounded pagination, and typed partial
  failures.
- Maintain complete account-history caching as one endpoint/ledger/account
  identity, with page size, cursor, list sort, and limit kept outside snapshot
  identity. Preserve the explicit no-point-in-time-guarantee field until an
  authoritative snapshot version exists.
- Add holder, supply, burn, and transaction aggregate reports from the
  identified official analytics authority.

### 2. NNS governance and economics

- Keep native NNS neuron list/detail and complete cache projections aligned
  with Governance's publicly readable `NeuronInfo` contract.
- Keep the native economics, cached metrics, latest reward-event, and maturity
  modulation reports aligned with the Governance query interface.
- Add broader reward history, delegation, and authenticated owner state only
  through an authority that truthfully exposes each field.
- Join governance enrichment to Registry topology only when each source keeps
  its own timestamp and provenance.

### 3. SNS completeness

- Keep SNS Root inventory, running module hashes, operational health, and typed
  inventory/summary gaps aligned with the native Root interface.
- Expand neuron and proposal state where the authoritative interface exposes
  it.
- Add swap, upgrade, and treasury reports with typed per-SNS follow-up gaps.

### 4. IC canister and network reporting

- Keep official Dashboard canister detail reporting aligned with the live API,
  including raw nullable fields, endpoint/retrieval provenance, and explicit
  non-certified, no-point-in-time claims.
- Keep Dashboard discovery bounded: count fetches no rows, page makes one call
  for at most 100 canister-id-ordered summaries, cursors require an explicit
  follow-up request, and neither operation creates a million-canister cache.
- Keep Dashboard metrics bounded: one aggregate metric and one explicit
  start/end/step request, at most 1,000 observations per returned series, no
  per-Subnet fan-out, and no implicit cache.
- Extend `LiveIcSource` with focused boundary-node location/detail,
  replica-version, daily-throughput, and trustworthy-metric capabilities.
- Keep Dashboard-derived analytics distinct from exact Registry or certified
  canister evidence.
- Add ICRC holder, supply, burn, and transaction aggregate reports through the
  official analytics API.

### 5. System and protocol canisters

- Add focused CMC/XDR and cycles reports needed for IC operating-cost evidence.
- Add Internet Identity, Bitcoin, XRC, and other protocol reports only when
  they form a coherent read-only family.
- Prefer typed capability traits over one adapter or command per remote
  method.

### 6. Stability and 1.0 preparation

- Audit every public request, report, error, adapter, and renderer for a stable
  ownership boundary.
- Define post-1.0 report-schema evolution and cache migration policy.
- Keep library code free of process output and the CLI free of report
  construction.
- Cover every public capability with fixture-backed API tests and targeted
  live smoke procedures.
- Document freshness, certification, and provenance expectations for every
  report family.

## Target CLI Contract

The current top-level authority families remain the foundation:

- `icq ic` for official Dashboard analytics with explicit REST provenance;
- `icq nns` for Registry and NNS governance evidence;
- `icq sns` for SNS discovery and per-SNS evidence;
- `icq icrc` for generic ledger, index, archive, and account evidence.

The global `--network` option must always be honored or rejected before
dispatch. NNS and SNS use it as target identity; the built-in sources and
caches currently accept only the mainnet `ic` identity. Dashboard canister and
ICRC reports use a stable entity id plus `--source-endpoint`; Dashboard metrics
use an official metric name, explicit time bounds, and `--source-endpoint`.
These families reject `--network`. No command may silently query a different
network from the one requested.

Every data-producing command documents whether it is a live query,
cache-backed read with refresh-if-missing, cache-preferred read with live
fallback, local-only cache inspection, forced refresh, or a view-dependent
choice between those modes.

The current command hierarchy uses singular entity families, separates
ledger-wide ICRC evidence from account-scoped queries, and makes account
transaction collection mode explicit:

```text
icq ic canister info|count|page
icq ic metrics <metric>

icq nns governance economics|metrics|reward-event|maturity-modulation
icq nns proposal list|info|refresh|cache
icq nns neuron list|info|refresh|cache

icq sns proposal list|info|refresh|cache
icq sns neuron list|refresh|cache
icq sns canister list

icq icrc ledger capabilities|token|index|transactions|block-types|archives|tip-certificate
icq icrc account balance|allowance
icq icrc account transaction page|list|refresh|cache
```

The remaining intended pre-1.0 grammar is not yet exposed:

```text
icq ic network
icq system xdr|cycles
```

Pre-1.0 hard cuts do not retain aliases for replaced forms. Unimplemented
`ic` and `system` commands should not be exposed as placeholders.

## Caching Policy

Caching is part of the product, but not every query should be cached by
default.

| Query class | Default policy |
| --- | --- |
| Exact Registry topology | One Registry version, atomic complete snapshot |
| Complete proposal, neuron, transaction, or analytics collection | Atomic complete snapshot with explicit refresh and attempt state |
| Small immutable metadata | Live query; cache only when it avoids repeated fan-out |
| Balance, allowance, exchange rate, or other rapidly changing point value | Live by default; an explicit snapshot may record it as evidence |
| Official REST analytics | Bounded point lookups live; complete collections or time series use timestamped snapshots with API endpoint provenance |
| External enrichment | Separate cache and timestamp; never inherit on-chain authority |

Cache keys identify collected data, not presentation choices. Sorting, limits,
verbosity, and text formatting remain views over a complete snapshot.

The CLI uses one user-level cache root across repositories:
`ICQ_CACHE_ROOT`, then `$XDG_CACHE_HOME/ic-query`, then
`$HOME/.cache/ic-query`. Public library requests receive that actual root and
do not append a hidden directory. The pre-1.0 cut does not discover, read, or
migrate former project-local `.icq` caches.

## Follow-Up Query Contract

Discovery should lead to normal typed follow-up requests:

1. a report exposes a stable Subnet, canister, ledger, index, archive, SNS, or
   account identifier;
2. the matching authority adapter accepts that identifier;
3. pagination or callback traversal is bounded and observable;
4. partial failures are retained as typed gaps or per-target failures;
5. the resulting report records every source needed to evaluate its freshness
   and authority.

There is no generic fallback to arbitrary Candid calls when a typed capability
is missing.

## 1.0 Completion Bar

Version 1.0 does not require covering every queryable canister. It requires a
stable and extensible reporting core with:

- complete topology and node-provider evidence;
- useful NNS proposal, neuron, reward, and economics reporting;
- ledger and index transaction history with archive and certificate handling;
- SNS discovery, governance, root inventory, and health;
- general canister and network metrics from an explicitly identified official
  source;
- CMC/XDR and cycles reporting;
- consistent adapters, provenance, errors, renderers, and cache operations;
- documented post-1.0 compatibility and schema-evolution rules.

The remaining system and protocol families may continue after 1.0 without
destabilizing those foundations.
