# 0.28 Design: Observed IC Node And Subnet Status

## Status

- Target: `0.28.0`
- Implementation: `0.28.0` and `0.28.1` released; `0.28.2` provider comparison
  reporting is complete in the current worktree
- Scope: official Dashboard node-status collection, one short-lived atomic
  snapshot, node/Subnet/provider projections, and terminology cleanup
- Authority: observed off-chain official Dashboard data
- Network: public mainnet identity `ic`

## Problem

The NNS Registry reports which nodes exist and which Subnet contains each
assigned node, but it does not report whether those machines are currently up,
down, degraded, or disabled. The official Dashboard node resource supplies
that operational observation together with node, Subnet, node-provider,
node-operator, alert, version, and location fields.

`ic-query` currently exposes Registry node and Subnet inventory plus joined
topology consistency reports. It cannot reproduce an operational summary such
as:

- degraded and down nodes grouped by Subnet;
- assigned and unassigned status totals;
- non-up nodes grouped by node provider; or
- the remaining Byzantine fault threshold implied by an observed Subnet size.

The existing `icq nns topology health` name also describes cache freshness and
join consistency, not machine or Subnet health. Keeping that name alongside an
operational status report would be ambiguous.

## Command Contract

0.28 adds these views over one shared snapshot:

```bash
icq nns node status
icq nns node status <node-or-prefix>
icq nns subnet status
icq nns subnet status <subnet-or-prefix>
icq nns node-provider status
icq nns node-provider status <provider-or-prefix>
```

Each command accepts `--all`, `--json`, `--refresh`, and an explicit
`--source-endpoint`. Without `--all`, node rows and aggregate rows with no
observed non-up nodes are omitted. Supplying an exact target or unique
principal prefix selects that target even when it is fully up. `--refresh`
forces one live replacement of the same complete snapshot before projection.

The existing command is hard-cut from:

```text
icq nns topology health
```

to:

```text
icq nns topology check
```

The corresponding public report, row, builder, renderer, and schema constant
use `Check` terminology. There is no compatibility alias or old command
parser.

## Source And Authority

The live source performs one HTTP GET against the official Dashboard v3
`nodes` resource. It uses the shared `LiveIcSource` HTTP boundary:

- credential-, query-, and fragment-free base endpoint validation;
- no redirects;
- a 30-second timeout; and
- an 8 MiB response-body ceiling before JSON decoding.

The source does not perform per-node, per-Subnet, or per-provider follow-up
calls. The unfiltered response is finite and must contain at most 10,000 rows.

The report records:

- `network: ic`;
- `authority: official_ic_dashboard_api`;
- the explicit source endpoint and caller-supplied collection timestamp;
- `certified: false`; and
- `point_in_time_guaranteed: false`.

Dashboard status is an off-chain observation. It is not an NNS Registry
record, a certified replica response, or proof that a node did or did not
participate in consensus at the collection instant.

The request intentionally uses the Dashboard's default public-mainnet node
scope. The API documents that this scope excludes cloud-engine Type4 nodes.
Reports and caches record that exclusion explicitly. The source must not
invent an open-ended reward-type list in an attempt to emulate an all-node
query.

## Raw Snapshot

One canonical row is retained for each node. Rows preserve the Dashboard's raw
operational classification and relevant evidence:

- node, node-operator, and node-provider principals;
- node-provider name;
- raw node type and reward type;
- raw `UP`, `DOWN`, `DEGRADED`, or `DISABLED` status;
- unknown future status/type text without treating it as healthy;
- raw alert name;
- assigned Subnet and cloud-engine Subnet identifiers when present;
- data-center id/name, owner, and region;
- GuestOS version and TEE observation;
- IP address and IPv4-connectivity observation; and
- hardware generation.

Node principals are canonical and unique. Optional principal fields, when
present, are canonical. Rows are ordered by node principal. Empty required
identifiers, duplicate nodes, contradictory assigned/unassigned evidence,
oversized collections, invalid provenance, and count inconsistencies are typed
source or cache failures.

Unknown status text is retained and counted separately. It contributes to the
conservative non-up count and can never make a report appear healthy.

## Cache Contract

The complete collected snapshot has one identity independent of target,
filter, sort, text verbosity, or aggregate view:

```text
ic/ic/nodes/operational-status/full.json
```

The snapshot uses schema version `1`, a sibling refresh lock, atomic
publication, and one API-exhausted completeness record for the non-paginated
resource. It is stale after 60 seconds. A refresh lock is stale after five
minutes.

The library keeps distinct operations for:

- strict cache-only load;
- forced live refresh;
- load or refresh missing/recoverably invalid; and
- load or refresh stale.

Ordinary CLI status views use stale refresh. Missing, malformed,
schema-incompatible, identity-invalid, semantically invalid, future-dated, or
expired snapshots visibly refresh and are replaced only after a complete new
snapshot validates. Filesystem errors remain strict. `--refresh` selects the
forced operation explicitly.

Validation never canonicalizes content loaded from disk. Cached node rows must
already be in strict principal order or the cache is invalid; live/custom rows
are validated first and canonicalized before atomic publication. An empty
mainnet node collection is invalid. Pure in-memory projections enforce the
same row, relation, scope, and ordering contract as source and cache paths.

`icq cache status` recognizes the snapshot's 60-second age policy and automatic
recovery policy.

## Projections

### Node status

The node report exposes snapshot-wide status and assignment totals plus the
selected canonical node rows. The default view returns every non-up row.
`--all` returns the complete snapshot. A target returns exactly one resolved
node.

Human-readable projections separate their provenance and summary preamble from
the first table with one blank line. Any later titled evidence table is a
separate visual section. This presentation rule does not alter JSON reports.

### Subnet status

Nodes with an assigned `subnet_id` are grouped by that exact principal. Each
row exposes total, up, down, degraded, disabled, unknown, and non-up counts,
plus the non-up node evidence that produced the aggregate.

For a Subnet with `n` observed nodes, the report derives:

```text
f = floor((n - 1) / 3)
```

and publishes both:

- additional `DOWN` nodes required to exceed `f`; and
- additional non-up nodes required to exceed `f`.

The second is the conservative Lorimer-style figure. It counts degraded,
disabled, and unknown rows as non-up, but is labelled as an estimate rather
than a claim that every such node is faulty. Zero means the corresponding
observed count already exceeds `f`.

### Node-provider status

Rows group exact node-provider principals and preserve the Dashboard's provider
name as off-chain enrichment. Each row exposes overall status totals plus a
complete status cross-tab for assigned, unassigned, API-boundary, and
unknown-assignment nodes. This retains the evidence needed to compare assigned
and unassigned up/down or conservative non-up counts without rescanning raw
rows. Each row also classifies unassigned versus assigned `UP` counts and
conservative non-up counts as `less`, `equal`, or `greater`. Report-level
comparison totals cover every observed provider before view filtering; text
renders the same direction explicitly and JSON preserves the typed outcomes.
Non-up node evidence is retained for diagnostics. Canonical provider ordering
is by principal and does not change with the text view or cache identity.

## Validation

Targeted tests cover:

- the live node URL and additive wire decoding;
- the 10,000-row ceiling, canonical principals, unique nodes, canonical order,
  raw unknown status retention, and contradictory assignment evidence;
- strict cache-only, forced refresh, missing/invalid recovery, stale refresh,
  fresh reuse, atomic replacement, and lock behavior;
- node, Subnet, provider, assigned/unassigned, API-boundary, unknown-status,
  and zero/nonzero threshold projections;
- all less/equal/greater provider comparison outcomes and snapshot-wide
  comparison totals before view filtering;
- exact and unique-prefix targeting plus unknown and ambiguous prefixes;
- source/cache provenance and cache-status registration;
- no-default public DTO/rendering availability;
- CLI help, default attention views, `--all`, `--refresh`, JSON, mainnet
  enforcement, alphabetical ordering, and namespace-help behavior; and
- the `topology check` hard cut through the supported current command and
  public API contracts.

No live-network test is required for unit or CI validation. Fixture sources
and local HTTP servers exercise behavior deterministically.

## Non-Goals

- certified node-liveness evidence;
- Prometheus scraping, background polling, notifications, or incident
  management;
- automatic NNS proposals or node replacement;
- joining this off-chain observation into exact-version Registry authority;
- retaining historical status events in 0.28.0;
- implicit per-row follow-up queries;
- including cloud-engine nodes by guessing reward-type filters; or
- compatibility aliases for `topology health`.
