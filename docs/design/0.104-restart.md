# IC Query restart at the 0.104 baseline

Status: accepted product direction with report contracts still to be designed.
The Cargo scaffold, [canister placement](canister-placement.md), selected
[subnet observation](subnet-observation.md) and
[registered subnet inventory](subnet-list.md) and
[certified subnet resource metrics](subnet-metrics.md) and
[two-sample subnet activity](subnet-activity.md) reports are implemented.
Canic infrastructure reports belong in `ic-topology`; SNS
migration belongs in the still-unimplemented `ic-sns-migration` shell.

## Purpose

Make IC Query a focused source of read-only evidence for Canic application
topology planning, uptime assessment and subnet maintenance. The product purpose
is defined in [AGENTS.md](../../AGENTS.md): support placement, capacity, performance,
cost, availability and trust decisions, rather than general-purpose IC querying.
The separate SNS migration crate has the narrow purpose defined below. Every
report must identify its Canic decision or SNS migration requirement, authoritative
source, bounded collection strategy and output contract.

Candidate decisions include whether to create ten cloud engines, consolidate
application workloads across subnets or consider a supported subnet merge, and
whether newly available TEE-enabled machines could reduce authentication overhead
under an explicit trust model. Reports must distinguish observed capabilities,
verified attestation, usable capacity and estimated benefits. These are planning
questions, not claims that a topology operation is available or that TEE hardware
automatically permits weaker authentication. Query does not execute the changes.

The legacy project grew across topology, governance, ledgers, dashboard data,
analytics, certification, caching and canister execution. Rebuilding all of that
would preserve the original breadth. Begin with a narrow vertical slice and add
another report only for an identified Canic infrastructure decision or the explicitly
limited SNS migration purpose.

## Package and report scope

`ic-query` names the repository and virtual Cargo workspace, with no umbrella
library. Its separate libraries are `ic-topology` for Canic infrastructure
observations and `ic-sns-migration` for the migration reads below. Neither library
depends on the other or on the CLI. Topology has no SNS module, feature or dependency.
Each will select only its required published Platform capabilities.

`ic-query-cli` (`icq`) composes specialist crates through compile-time command
adapters. Add adapter modules, package dependencies and optional features when
there are implemented commands to use them. No runtime plugin discovery or
dynamic loading is planned. A future NNS requirement would need a separately
approved crate and CLI adapter; it would not expand `ic-topology` into governance.

Reuse Platform's Agent, DTOs, codecs and cryptography, Platform Types identities
and IC Tooling Host utilities where needed. Add a shared helper crate only after
multiple specialists demonstrate a common contract those suppliers do not own;
do not prebuild a generic query-core layer. The placement report now selects
Platform's Agent and Registry DTO capabilities; SNS has no runtime dependencies.

Use modules inside the main library, not a package or repository per IC entity:

| Module | Responsibility |
| --- | --- |
| `topology` | Joined node, operator, provider, data-center, subnet and cloud-engine inventory; scoped placement views |
| `capabilities` | Hardware and TEE evidence, subnet features and relevant software configuration |
| `resources` | Resource observations, subnet progress and scoped uptime/maintenance evidence |
| `costs` | Relevant cloud-engine prices, conversion rates and resource-pricing inputs |
| `changes` | Compare supplied observations for new machines, assignment, capability and maintenance changes |

Provider/region summaries and version views project the same underlying evidence.
Preserve differences between subnet classes and between configured, observed and
verified facts. Provenance, verification, limits and coverage are shared report
mechanics. Comparison does not itself require persistent collection or a scheduler.

| Responsibility | Initial treatment |
| --- | --- |
| Canic infrastructure reports | Single-canister placement and selected-subnet certified node-key observations implemented; further report contracts remain open |
| SNS migration evidence | Separate crate: balances and neuron information for an explicitly selected SNS |
| Bounded native IC queries | Use the published Platform Agent capability, explicit endpoint policy and typed external DTOs |
| Typed reports and script-friendly JSON | Each library owns its reports; the CLI owns presentation |
| Terminal output, CLI parsing and progress | Keep in the CLI; rendering remains pure and independently usable |
| Cryptographic verification | Use supplying Agent/Platform capabilities where the selected report needs them; distinguish verified from observed data |
| Persistent caches, refresh locks and background collection | Defer; start with bounded on-demand reads |
| Broad scans and historical collection | Defer; any collection must serve a scoped Canic infrastructure decision |
| Generic token analytics, holder indexing and network-wide canister exploration | Excluded |
| Cloud-engine and subnet reports | Candidate core scope where they inform Canic topology decisions; exact reports remain to be selected |
| Dashboard aggregation | Outside the initial proposal; any future source must serve an identified Canic decision |
| Canister/Wasm adapters, generated probes and Testkit workspace | Outside the initial proposal; require a concrete embedding need to restore |
| Deployment, mutations and arbitrary canister invocation | Outside the product boundary |

NNS proposals, voting, neurons, maturity, governance analytics and Node Rewards
reports/adapters are excluded, including Node Rewards as an indirect performance
source. NNS Registry topology reads remain in scope.
Generic ledger history, holder/token analytics, provider-payment history,
canister search and replica-release catalogues are not retained report families.
Keep only the balance/metadata reads required by SNS migration, and infrastructure
reads needed by Canic. Boundary-node geography and general network presentation
remain deferred unless an endpoint-selection requirement justifies them.

## Uptime, maintenance and data sources

Uptime reports must define their target, observation window, sampling, coverage
and unknown intervals. Preserve endpoint failures separately from evidence of
subnet failure. Registration, assignment, resource counters and progress each
answer different questions; none alone establishes allocatable capacity or a
complete uptime history. Maintenance observations may include configuration and
software changes, but a schedule or cause must have its own identified source.
Do not reconstruct an NNS proposal explorer to explain maintenance.

Investigate direct Registry and certified-state reads first, then relevant
cloud-engine control-plane reads. New management metrics may require a canister
caller; their need does not implicitly authorize deploying a relay or restoring
the legacy canister adapter. Dashboard collector data may supply explicitly
identified historical context when needed, but stored on-chain observations are
not automatically live, complete or certified. Qualify each source and its caller
restrictions before implementation; keep external DTOs and codecs in Platform.

Query supplies evidence and comparisons. Canic combines them with application
requirements to plan topology and maintenance; Auth owns supported authentication
strategies. Query neither decides to weaken authentication nor executes changes.

## SNS migration boundary

The independent `ic-sns-migration` crate supports users of Motoko, Toko,
Dragginz and similar applications leaving SNS-based
systems for our new platform. The only SNS report capabilities selected are
balances and neuron information for a specified SNS. Source resolution and bounded
pagination may support those reports; this does not select a network-wide SNS
directory, governance explorer or historical analytics service.

This limited investment reflects the maintainers' concern that SNS may be replaced
or removed by the Foundation. That concern is a planning rationale, not a verified
claim about Foundation plans. Full SNS support is not a product objective regardless
of whether that possibility materializes.

Keep SNS proposals, voting, swap operations, treasury analytics, framework upgrades
and neuron management outside this surface. Query reads migration evidence;
the destination platform owns eligibility, entitlement mapping and migration
execution. Do not infer a transfer or claim process from this reporting scope.

Before implementation, identify the target SNS and account/neuron selectors,
required raw fields, source canisters, completeness bounds and observation-time
requirements with the migration consumer. Preserve provenance and verification
status. Separate reads must not be described as an atomic migration snapshot
without evidence establishing that guarantee.

## Ownership and data flow

Proposed flow:

```text
CLI arguments
    -> explicit endpoint + request + limits
    -> library report operation
    -> narrow source adapter
    -> Platform Agent / external DTOs / bounded codecs
    -> typed report + provenance or typed failure
    -> JSON serialization or pure CLI text rendering
    -> CLI-owned stdout/stderr
```

The library owns request semantics, report construction, bounded collection,
completeness and error projection. Source traits are introduced only where a real
network boundary needs fixture substitution; avoid a universal query engine or a
second Agent abstraction.

Platform owns external protocols, certificate/hash-tree types and bounded codecs.
Agent owns authentication. Query sets endpoint/root-key admission, reply budgets,
call deadlines and any report-specific retry policy. Do not route IC calls through
ICP CLI JSON envelopes, copy external protocol definitions, or implement another
cryptographic stack.

The CLI owns Clap parsing, command dispatch, terminal detection, process IO and
progress rendering. Text rendering and report-specific amount/unit formatting
belong in its presentation module; shared formatting mechanics use Host Text when
needed. Core code must neither depend on that module nor write to stdout/stderr.

The scaffold uses Rust 2024 and the adopted compiler/lint policy. Keep modules
at real ownership boundaries, use directory `mod.rs` for modules with children,
and place test bodies in adjacent test files. Do not recreate the legacy feature
matrix before a selected consumer needs it.

## Report guarantees

Each implemented report must specify:

- The selected endpoint, network/canister identity, source method and fetch time.
- Whether data is certified, authenticated, merely observed, or unavailable;
  missing proof must not be represented as successful certification.
- Exact raw quantities and identifiers in typed/JSON output. Human formatting
  must not destroy values used by scripts.
- Explicit reply-byte, collection/page/item and time limits. Exceeding a limit
  produces a typed outcome; never silently claim a truncated result is complete.
- Typed failure categories with original causes retained. Retry decisions use
  structured facts and a bounded policy, not diagnostic string matching.

A complete snapshot is exposed only after its collection succeeds. An operation
that deliberately returns partial observations must name that contract and expose
its omissions; it must not masquerade as a complete report.

No implicit live network work belongs behind an apparently cache-only operation.
If persistence is later justified, define storage ownership and failure/recovery
semantics first. Cache identity describes collected data; sorting, limits used
only for display and verbosity are view policy. Do not reuse legacy cache paths.

CLI commands follow `icq <specialist> <entity> <action>`. Each specialist has a
compile-time adapter; `topology canister show` and `topology subnet show` expose
the implemented reports. Entity namespaces do not accept bare IDs.
The [`topology subnet list` contract](subnet-list.md) specifies the
Registry inventory source and bounds, using Platform's Registry protobuf capability.
For CLI namespaces, bare invocation prints the same complete local help as the
explicit help subcommand and exits successfully. Invalid scope values and
incomplete leaf operations remain errors. Commands, including generated `help`,
are alphabetical through the shared command-tree boundary. Separate report
metadata and subsequent tables with a blank line.

## What carries forward

Keep the read-only product restriction, evidence guarantees, canonical supplier
boundaries, raw JSON values and pre-1.0 schema-1 rule. Keep consumer obligations
attached to existing package names even where new specialists replace them.

Use the legacy checkout to identify existing contracts and consumers. Do not copy
its source tree, cache machinery, release recovery state, historical design set,
private qualification workspace or dependency catalog as a starting implementation.
The legacy repository remains the owner of that history and evidence.

Before a public replacement, inventory affected library callers, CLI integrations,
public presentation users and persisted reports/caches. Record each retained or
retired contract, its affected consumers and their update/reset disposition. Search
only task-relevant consumers and respect repository exclusions. A fresh directory
does not demonstrate that old consumers or retained evidence are disposable.

## Version and crates.io continuity

“Retain 104” means retain the **0.104 version line as the restart baseline**, not
restart at 0.1 or introduce new package names merely to avoid compatibility work.
The inspected legacy manifests are `ic-query 0.103.1` and
`ic-query-cli 0.104.1`; their pending notes are `0.103.2` and `0.104.2` respectively.
These are local observations, not a fresh registry publication inventory.

The earlier scaffold-only `0.104.2` draft was not published. The new specialist
libraries are drafted at `0.104.0`; the incompatible CLI replacement is drafted at
`0.105.0`. Registry checks on 2026-11-14 found the legacy CLI at `0.104.1` and no
published `ic-topology` or `ic-sns-migration` index entries. These development
versions do not reserve names or authorize publication. Every package currently
inherits `publish = false`. The [local publication hold](../../AGENTS.md#delivery-and-publication)
keeps publication deferred until maturity and explicit maintainer authorization;
push requests are versioned GitHub-only delivery. Each push prepares the next
appropriate version of changed groups and their manifests, lockfile and notes;
already delivered versions are not reused. The compatible resource-metrics
batch delivered CLI `0.105.1` and topology `0.104.1` to GitHub. The
subnet-classification API change requires topology `0.105.0`; classification
and two-sample activity additions select CLI `0.105.2` for this GitHub delivery.
SNS remains at `0.104.0`. No new push is implied by
ordinary implementation or continuation.

Topology, SNS migration and CLI own independent release ledgers under `releases/`;
the root changelog is their index. The group map is declared in
[`ci/cargo-release-groups.json`](../../ci/cargo-release-groups.json); CLI examples
belong to the CLI ledger. Keep explicit package versions rather than a
shared workspace version. Recheck registry versions, ownership and combined
consumer impact before publication. Renaming the library does not retire the old
`ic-query` contract automatically: document caller migration and retained-evidence
disposition before replacement. Never squeeze removed CLI commands into a patch.

Query-owned emitted/persisted schema identifiers stay at `1` before 1.0. An
incompatible format replacement requires an explicit old-format retirement/reset
and coordinated consumers, not a second reader or schema bump. Preserve caller
records and external obligations throughout that decision.

Publication readiness later requires real manifests, package metadata and root
licence inheritance, qualified native hosts, archive validation, registry checks
and the adopted release runner. No release adapters, tags, pushes, publication or
credentials are introduced by this scaffold.

## Implementation sequence

1. Select the first Canic topology, uptime or maintenance decision, its report and
   required fields; finalize the needed CLI surface. Keep SNS implementation in
   its separately scoped crate.
2. Specify the typed/JSON contract, endpoint policy, bounds, failure behavior and
   consumer impact for that report before implementing it.
3. Extend the established package shells, exact tooling pin/member inheritance,
   lockfile, shared Make interface and compiler/lint policy as the report needs.
4. Implement one vertical slice with fixture-backed source tests and CLI contract
   tests. Add live integration qualification only for the selected protocol need.
5. Review what remains necessary before adding a second report. Keep cache,
   canister, indexing and analytics machinery deferred without a demonstrated need.
6. Coordinate affected consumers and retained data, then qualify and publish under
   a separately requested release workflow with appropriate package versions.

Required native support remains Linux x86-64 and macOS ARM64/x86-64. The legacy
matrix used Ubuntu 24.04, macOS 15 ARM64 and macOS 15 Intel. This is a support
requirement. The [setup guide](../development/setup.md#focused-validation-and-qualification)
records successful hosted checks for the implemented contracts on all three hosts.

## Decisions still open

  support, and what workload, observation-window, capacity and trust inputs are needed?
- How will Canic consume the library reports, and which CLI commands or public
  presentation APIs are needed?
- Which SNS balance and neuron fields, selectors and observation guarantees does
  the destination platform require for user migration?
- Which legacy public contracts and retained data need explicit retirement?

Scaffold qualification covers Cargo/snapshot agreement, formatting, linting,
documentation and the CLI's actual help/version/error behavior. Native CI selects
all three required hosts; the setup guide records the successful run and source commit.
The placement and subnet reports add bounded projection and failure fixtures; broader
inventory and uptime implementation and qualification remain subsequent tasks.
Keep ordinary tests with their package; create a separate `qualification/`
workspace only when a real test-only package is needed.
