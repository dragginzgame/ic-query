# 0.35 Design: CloudEngine Type4 Node Reporting

## Status

- Status: implemented for the 0.35 release slice
- Authority: official IC Dashboard v3 node resources
- Collection mode: one response-bounded live REST request
- Public family: `ic_query::cloud_engine`

## Purpose

The existing default Dashboard node-status snapshot deliberately follows the
upstream public-mainnet default, which excludes CloudEngine nodes. The node
resource now documents an explicit reward-type filter that selects Type4
CloudEngine nodes and supports stable node, provider, status, and CloudEngine
Subnet fields. That evidence belongs below the top-level CloudEngine family
while retaining Dashboard provenance.

```bash
icq cloud-engine node list
icq cloud-engine node list --node-provider-id <node-provider-id>
icq cloud-engine node info <node-id>
```

`node list` is network-wide unless given an exact node-provider principal.
`node info` targets one node principal. Neither target is a CloudEngine
Subnet, operator canister, engine canister, or provider aggregate.

## Collection Contract

`CloudEngineNodeSource` is a focused capability on the existing
`LiveIcSource`. List sends one `/nodes` request with
`include_node_reward_type=Type4`, repeated `include_status` parameters for
`DOWN`, `UP`, `DISABLED`, and `DEGRADED`, and `sort_by=node_id`. When supplied,
`node_provider_id` is included as one exact remote filter. Exact info
canonicalizes its target and requests `/nodes/{node_id}` once.

Both operations use shared credential-free HTTP(S) endpoint validation,
redirect rejection, synchronous runtime ownership, and the 8 MiB response
ceiling. A list admits at most 10,000 rows and may be empty after an exact
provider filter. Exact info requires one row. No pagination or per-node
follow-up is performed.

The live source echoes the requested provider, reward type, and ordered status
scope in `CloudEngineNodeListSourceData`. Report construction rejects a custom
source that changes that intent. It then applies the same canonical raw-node
validation used by observed node status: canonical principals, unique node
ids, bounded text, consistent provider names, canonical node-id ordering, and
valid optional ordinary and CloudEngine Subnet principals. Every list row and
the exact row must retain raw reward type `Type4`; filtered lists additionally
require each status to belong to the explicit request scope.

## Report Contract

Schema-1 reports flatten `IcDashboardReportProvenance`. The raw row is the
shared `IcNodeStatusRow`, publicly named `CloudEngineNodeRow` at the product
boundary. JSON therefore retains:

- node, operator, provider, ordinary Subnet, and CloudEngine Subnet ids;
- raw status, node type, reward type, alert, provider name, and assignment;
- data-center id/name, owner, and region;
- GuestOS version, TEE state, IP address, IPv4 connectivity, and hardware
  generation.

List reports also retain the exact filter scope and report row count, raw
operational-status totals, distinct provider count, distinct non-null
CloudEngine Subnet count, and null-assignment count. Counts are projections of
the returned node rows. They are not reconciled with or substituted for the
Dashboard's separately timed node-provider aggregate fields.

Text separates provenance and summary metadata from the node table with one
blank line. Exact info presents the complete raw row as labelled fields. Null
optional values remain visible rather than being inferred.

## Authority Limits

Reports state `authority: official_ic_dashboard_api`, `certified: false`, and
`point_in_time_guaranteed: false`. Status and assignment are timestamped
off-chain observations. They do not prove Registry membership, certified
liveness, reachability from a particular client, native control-plane state,
or agreement with another Dashboard request.

The provider filter establishes provider-to-node detail within this one node
resource because each returned row carries a stable provider principal. It
does not manufacture a join from provider location aggregates. The exact node
lookup establishes stable follow-up identity but does not make the row
certified.

## Public Library Boundary

Pure no-default builds expose node requests, reports, the shared row alias,
bounds, filter constants, and text renderers from `ic_query::cloud_engine`.
`dashboard-host` adds `CloudEngineNodeSource`, source-data DTOs,
live/custom-source builders, and the implementation on `LiveIcSource`.

The public default endpoint is now
`DEFAULT_CLOUD_ENGINE_DASHBOARD_SOURCE_ENDPOINT`, shared by provider and Type4
node reports. The provider-specific old name is removed without an alias under
the pre-1.0 hard-cut policy. `cloud-engine-host` continues to own only native
control-plane calls through `LiveCloudEngineSource`.

## Cache Contract

Both operations are live-only and do not read, write, invalidate, or migrate a
cache. The existing 60-second observed node-status cache is keyed to the
Dashboard default public-mainnet scope, which excludes CloudEngine nodes.
Explicit Type4 filters therefore form a different collected-data identity and
must not reuse that cache. Adding persistence would require its own freshness
policy and complete-snapshot contract.
