# 0.37 Design: ICRC Account and Holder Index Reporting

- Status: implemented for the 0.37 release slice
- Scope: one bounded account page, exact account detail, and one bounded holder
  page
- Authority: official IC Dashboard ICRC REST API
- Persistence: none

## User contract

```bash
icq icrc analytics account list mxzaz-hqaaa-aaaar-qaada-cai --limit 25
icq icrc analytics account info mxzaz-hqaaa-aaaar-qaada-cai <account-id>
icq icrc analytics holder list mxzaz-hqaaa-aaaar-qaada-cai --sort-by=-balance
```

Each operation makes exactly one live request. It performs no native ledger or
index-canister query, follows no cursor automatically, and reads or writes no
cache. These are off-chain Dashboard index records with `certified: false` and
`point_in_time_guaranteed: false`.

## Account pages

`account list` requests the official v2 ledger account resource. It accepts:

- a limit from 1 through 100, default 20;
- an optional canonical owner-principal filter;
- one opaque exclusive `after` or `before` cursor; and
- the upstream id, balance, transaction-count, creation-time, or owner sort in
  ascending or descending order.

The report preserves the requested owner, cursor, limit, and exact API sort
value. It returns the response's opaque previous and next cursors without
claiming that a cursor exists whenever more rows exist.

The API encodes a composite sort cursor as one comma-separated response string
but accepts its one or two components as repeated query parameters. The public
request and report deliberately keep that cursor as one opaque string so a
caller can reuse it unchanged. Only the live HTTP boundary splits it. Empty
cursors, more than two components, and simultaneous forward/backward cursors
are rejected before a source call.

Pages are not merged, scanned, deduplicated across calls, or described as a
complete snapshot. Rows must have unique ids within one response; an owner-
filtered response must contain only that owner.

## Exact account detail

`account info` requests the official v1 exact-account resource using the
opaque stable id returned by account list. It does not require the id to be a
principal because non-default subaccounts can have a distinct index identity.
The returned id must exactly match the requested id.

Account rows retain:

- opaque account id, canonical owner, and raw subaccount text;
- raw indexed balance in ledger base units;
- total and latest indexed transaction evidence;
- active fee-collector state and raw block-range arrays;
- canonical ledger identity; and
- the raw Dashboard database update timestamp.

## Holder pages

`holder list` requests the official v2 principal-level holder resource. It has
the same 1-through-100 limit and opaque forward/backward cursor contract as
account list, with balance, transaction-count, creation-time, or principal
sorts.

A holder is an API aggregate, not an ICRC account. Each row keeps the canonical
principal, aggregate raw base-unit balance and transaction count, latest
transaction index, raw numeric supply percentage, nullable raw USD value,
ledger identity, and raw Dashboard update timestamp. No market-value
normalization or endorsement occurs.

## Timestamp normalization

The upstream `created_timestamp` is a Unix timestamp in nanoseconds. Public
rows expose:

- `created_at_unix_secs`, the ordinary Unix timestamp in seconds; and
- `created_at_subsec_nanos`, the exact remainder below that second.

This makes the primary timestamp directly usable while preserving the full
upstream precision. `updated_at` is a separate Dashboard database string and
remains raw as `dashboard_updated_at`.

## Provenance and validation

Every report flattens shared schema-1 Dashboard provenance: network `ic`,
authority `official_ic_dashboard_api`, exact endpoint and collection time,
`certified: false`, and `point_in_time_guaranteed: false`.

Before projection, the adapter validates request bounds, ledger and optional
owner principals, echoed query and provenance, row-count bounds, canonical row
principals and ledger identities, unsigned decimal balances, non-empty update
times, numeric holder percentages, exact account identity, and within-page
uniqueness. Creation nanoseconds are split with integer arithmetic; no float
conversion is used.

## Ownership

- CLI parsing and dispatch remain under `ic-query-cli`'s ICRC analytics
  namespaces.
- Pure request/report types remain under `ic_query::ic`, matching the
  Dashboard authority used by the existing ICRC analytics reports.
- `IcIcrcIndexSource` owns the focused account/holder host capability.
- The live adapter owns version-specific URLs, cursor parameter translation,
  and wire decoding.
- Text rendering is human-facing; JSON preserves raw identifiers and values.

## Explicit exclusions

This slice does not:

- enumerate all accounts or holders;
- infer circulating supply from holder rows;
- reconcile indexed balances with a current native ledger query;
- cache pages or exact records;
- add a holder-detail operation that the official API does not expose; or
- claim stronger freshness, completeness, or certification than the API.

## Verification

Fixture tests cover request-before-source validation, cursor bounds, query and
identity matching, timestamp normalization, report rendering, CLI parsing and
help, and public Rust API construction. Live smoke verification covers a
descending two-row account page, an exact account lookup, a descending two-row
holder page, and composite cursor translation.
