# 0.32 Design: Bounded Replica-Version Reporting

## Status

- Status: implemented for the 0.32 release slice
- Authority: official IC Dashboard REST API
- Collection mode: one bounded live page or one exact live detail lookup
- Public family: `ic_query::ic`

## Purpose

The official Dashboard exposes release-election records separately from the
Registry's desired Subnet configuration and from the version a Subnet is
actually running. `ic-query` adopts that bounded off-chain resource without
collapsing those three meanings:

```bash
icq ic replica-version list --limit 25
icq ic replica-version info e3d101b22ae3fa02aca737f9fb96cc6c4ca83ac3
```

The singular `replica-version` entity family sits below `icq ic` because the
Dashboard is its authority. It is not a Registry or NNS Governance report even
though rows identify the NNS proposals that elected releases and assigned
Subnets.

## Request Contract

`replica-version list` sends exactly one request to
`subnet-replica-versions`. It accepts:

- `--limit`, defaulting to 50 and capped at the API maximum of 100;
- a zero-based `--offset`, defaulting to zero; and
- an optional `--max-proposal-index` ceiling returned by an earlier page.

The live adapter explicitly requests descending execution-time order and the
documented `EXECUTED`, `OPEN`, and `ADOPTED` statuses. It does not automatically
follow an offset. The response's `resolved_max_proposal_index` can be supplied
as the next request's ceiling so later indexing does not raise the selected
upper bound; this remains an off-chain pagination aid, not a certified snapshot
version or a point-in-time guarantee.

`replica-version info` validates one exact 40-character lowercase hexadecimal
identifier and sends exactly one detail request. A missing record is the
Dashboard HTTP error; the command does not scan the list or perform a fallback
lookup.

Both commands use the shared credential-free HTTP(S) endpoint validation,
30-second timeout, redirect rejection, and 8 MiB response limit.

## Report Contract

The bounded list report preserves:

- the exact limit, offset, and optional requested proposal-index ceiling;
- the resolved proposal-index ceiling, matching total, returned count, and
  derived next offset;
- raw release identifiers, election proposal ids and execution timestamps;
- typed raw Dashboard lifecycle status;
- raw title and discussion URL, including empty values on historical rows; and
- each Dashboard-recorded Subnet rollout principal, proposal id, and execution
  timestamp.

List rows omit the potentially large release-note summary. The exact info
report preserves that raw summary in JSON along with the same release and
Subnet rollout evidence. Human text truncates list titles to 80 characters and
the exact summary to 240 characters after escaping control characters; JSON is
not truncated.

Projection rejects an invalid release identifier, zero election proposal id,
an `EXECUTED` row with a zero execution timestamp, duplicate proposal rows, a
page larger than its requested bound, inconsistent pagination
totals, ascending rows under the requested descending sort, noncanonical
Subnet principals, zero or duplicate rollout proposal ids, and mismatched
custom-source query, provenance, or exact target. Rollouts are canonically
ordered by execution timestamp, proposal id, and Subnet principal.

The Dashboard uses a raw execution timestamp of zero for release-election and
Subnet-rollout proposals that have not executed. The report preserves that
value instead of converting it to a collection time or inventing an optional
date.

## Authority and Runtime Meaning

Both reports use the shared Dashboard provenance:

```text
network: ic
authority: official_ic_dashboard_api
certified: false
point_in_time_guaranteed: false
```

A release election and its Dashboard-recorded Subnet rollout proposals do not
prove which binary a Subnet is currently executing. The Registry records
desired configuration, and an upgrade completes later at a consensus epoch
boundary. This slice deliberately adds no Dashboard/Registry join, node
follow-up, CUP lookup, or `current` label.

## Public Library Boundary

Pure builds expose the requests, reports, rows, status enum, constants, and
text renderers. The existing `dashboard-host` feature additionally exposes
`IcReplicaVersionSource`, live/custom-source builders, source-data contracts,
and the `LiveIcSource` implementation. No dependency or feature is added.

## Cache Contract

Replica-version reports are live-only. They do not read, write, invalidate, or
migrate cache files. An explicit page is a view over an off-chain index, not a
complete collection suitable for publication as a network snapshot.

## Scope

This slice does not:

- claim the Registry's configured version is currently running;
- query or verify catch-up packages or node binaries;
- auto-page or build complete release history;
- copy large release summaries into list rows;
- join release records to cached topology;
- claim certified or point-in-time evidence; or
- create a cache.

Useful later work is a separately named desired-versus-observed version report
only when a bounded source exposes trustworthy runtime evidence. Individual
boundary-node detail, broader daily analytics, and certified metrics remain
independent Dashboard slices.
