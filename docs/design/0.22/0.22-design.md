# ic-query 0.22 Design: Structural Consolidation

## Status

- Status: active
- Release line: `0.22.x`
- Decision style: behavior-preserving internal consolidation with explicit
  pre-1.0 hard cuts only where public Rust contracts are deliberately replaced

## Goal

The `0.22.x` line reduces repeated parsing, cache, Registry-inventory, and
projection machinery before the reporting surface expands further. The work
keeps the authority-oriented adapter architecture defined in
[IC Reporting Adapters](../ic-reporting-adapters.md): one built-in live adapter
per authority family, small capability traits at report boundaries, and no
universal query or arbitrary-Candid fallback.

Consolidation is successful when one invariant has one implementation owner,
while report-specific authority, validation, provenance, and rendering remain
explicit. Reducing file or line counts alone is not a reason to merge distinct
protocol contracts.

## Preserved Contracts

Every `0.22.x` slice preserves these contracts unless its changelog explicitly
identifies a pre-1.0 hard cut:

- read-only behavior and explicit network endpoints;
- no hidden live calls behind cache-only commands;
- stable report JSON, cache identity, cache schemas, and canonical ordering;
- distinct live, cache-only, refresh, refresh-missing, and refresh-stale
  behavior;
- one live adapter per IC authority family and focused custom-source traits;
- exact Registry-version joins and atomic publication where already promised;
- process output owned exclusively by `ic-query-cli`;
- raw IC terminology and authority-specific provenance;
- no compatibility aliases, fallback readers, dual parsers, or deprecated
  wrappers.

Cache keys continue to describe collected data. Text verbosity, JSON selection,
sorts, and limits remain view options and do not create new snapshot identities.

## Workstream 1: Public-Surface And Test Hygiene

Replace wildcard public re-exports with explicit family-root exports so adding
an internal item cannot accidentally expand the supported Rust API. Consolidate
mechanically repeated test setup and assertions into table-driven cases without
removing current-contract coverage.

This workstream must not change public paths, command grammar, help, errors,
reports, cache behavior, or network calls. Public-API tests remain the proof
that the explicit export list is complete.

## Workstream 2: Published Documentation And Embedder Features

Both crates publish the repository README. Every README link needed by a
crates.io reader therefore resolves to the canonical GitHub document instead
of assuming the package archive contains the repository-level `docs/` tree or
root changelog.

The library exposes a `subnet-catalog-host` feature for downstream crates that
need the live/cache subnet catalog without the full reporting host. It includes
the IC agent, Registry protobuf decoding, hashing, synchronous Tokio bridge,
cache IO, and endpoint validation required by that API. It deliberately
excludes Dashboard Reqwest transport and CBOR certification dependencies.

The existing `host` feature is a strict superset and remains the feature used
by `ic-query-cli`. The narrower feature does not create a second subnet API,
adapter, cache schema, or behavior path; it compiles the same
`ic_query::subnet_catalog` contract with a smaller dependency closure.

## Workstream 3: One Composed Clap Command Tree

The current CLI constructs presentation commands, reduced dispatch commands,
and nested passthrough parsers. It also scans raw arguments for help, version,
and global-option placement and forwards the selected network through a hidden
internal option.

Replace that staged grammar with one composed Clap tree that owns:

- top-level, family, group, and leaf subcommands;
- help and version handling;
- global option placement and validation;
- the shared `--json` view flag;
- typed leaf dispatch data.

Parsing remains in `ic-query-cli`; report construction remains in the matching
library report module. NNS and SNS command families remain separate. The
composed tree must remove obsolete passthrough commands, manual help/version
recognizers, and hidden option forwarding in the same hard cut.

Command names, supported options, output selection, exit-code classes, and
network authority remain unchanged. Exact whitespace or ordering in generated
help and parse diagnostics may change because Clap becomes their sole owner;
that observable change must be recorded in the release changelog.

Delivered in `0.22.1`: one top-level parse now returns the typed match tree used
by every family and leaf dispatcher. Native Clap owns `-h`/`--help`, nested
`help <path>`, propagated `-V`/`--version`, required-subcommand diagnostics,
and top-level `--network` validation. The old trailing positional `... help`
recognizer, reduced passthrough grammars, raw global-option scans, and hidden
network-forwarding option were removed together. The selected network is
passed explicitly from the root match tree to NNS, SNS, and system dispatch.

## Workstream 4: NNS Registry Inventory Orchestration

Node, node-provider, node-operator, and data-center reports share the same
Registry inventory lifecycle: cache lookup, explicit refresh policy, mainnet
enforcement, source fetch, atomic cache publication, list projection, and
exact-or-unique-prefix resolution.

Introduce small internal inventory-family contracts and concrete helpers. They
may share lifecycle and resolution mechanics, but each family continues to own:

- its public request/report/row/source contracts;
- Registry record projection and validation;
- family-specific not-found and ambiguous-input errors;
- cache filename, report schema version, and text renderer.

Prefer associated types or concrete helper traits over helpers with more than
three generic parameters. Do not introduce a universal NNS adapter or combine
the four public report families merely because their orchestration is similar.

A later deliberate public-error or provenance consolidation would be a
pre-1.0 Rust-API hard cut. It must remove the replaced fields and variants
without aliases and receive its own changelog compatibility note.

## Workstream 5: Snapshot Lifecycle Consolidation

NNS proposal/neuron and SNS proposal/neuron caches share attempt tracking,
refresh locking, progress, completeness validation, atomic publication, and
cache-status mechanics. Move those mechanics into the existing shared snapshot
and cache helpers where the behavior is genuinely identical.

Family implementations retain their own pagination, row validation, cache
identity, typed application errors, source authority, and report projection.
An abstraction must not erase these distinctions or require a generic type with
an unwieldy parameter list.

The NNS proposal and neuron families share one Governance-specific adapter for
attempt JSON construction, strict sidecar reads, shared metadata validation,
report-safe status projection, and failed-progress recovery. They continue to
map invalid attempt evidence into their existing family-specific errors. The
generic `snapshot_cache` owner remains responsible for locking, paged progress,
completeness, atomic publication, and finalization ordering.

The SNS proposal and neuron families share one SNS refresh owner for target
lookup, network validation, lock acquisition, resolved context, cache-envelope
provenance, completeness metadata, atomic publication, and attempt
finalization. Their proposal-id and neuron-byte cursors, page validation,
collection rows, cache schemas, reports, and source capabilities remain
separate. SNS continues to use its own canister authority, attempt metadata,
and public errors rather than inheriting the NNS Governance adapter.

For every migrated cache family, fixture tests must prove unchanged behavior
for:

- missing and valid complete snapshots;
- corrupt or incomplete snapshots;
- running, complete, and failed attempt evidence;
- stale and active refresh locks;
- partial fetch failure and attempt finalization failure;
- canonical ordering, uniqueness, and API-exhaustion guarantees.

## Workstream 6: Cohesive Module Boundaries

Split large modules only at real protocol or ownership boundaries:

- ICRC account-history collection, generic index wire conversion, and ICP index
  wire conversion;
- ICRC request contracts and report/row contracts;
- IC Dashboard network, metric, and canister capability internals;
- large renderer modules by coherent report family.

Conversely, merge one-function leaf modules that own no parsing, IO, cache,
protocol, validation, or reusable formatting boundary. Avoid creating a mirror
image of the same fragmentation under new directory names.

The generic ICRC index and deployed ICP index remain separate wire contracts.
Dashboard, Registry, Governance, ledger, and certified-canister provenance
remain distinct even when their Rust fields look similar.

Delivered in `0.22.2`: ICRC account-history live orchestration, arbitrary-Nat
cursor validation, complete paged collection state, generic ICRC-index wire
conversion, and deployed ICP-index wire conversion have separate internal
owners. The shared wire owner contains only the common request envelope,
response-codec selection, and protocol-neutral projection helpers. Public Rust
paths, report and cache schemas, cursor semantics, raw transaction JSON, index
discovery, and live call ordering are unchanged. That slice left
request/report-contract, Dashboard-internal, and renderer boundary work for
later delivery.

Delivered in `0.22.3`: the mixed ICRC public-contract module is now an explicit
internal facade over separate request and report/row owners. Request
constructors and cache/view identity no longer share an implementation file
with serialized evidence schemas. The existing `ic_query::icrc::*` paths,
feature availability, derives, constructors, fields, and JSON contracts are
unchanged. Dashboard-internal and renderer boundary work remains pending.

## Ordered Delivery

1. Public export hygiene and table-driven duplicate tests.
2. Published README links and the focused `subnet-catalog-host` feature.
3. Internal NNS Registry inventory lifecycle and resolver sharing.
4. Shared NNS Governance snapshot-attempt mechanics.
5. Shared SNS proposal/neuron refresh and publication mechanics.
6. One composed Clap command tree.
7. Large-module boundary cleanup after the shared owners are stable.

Each step lands with a clean compilation and focused tests before the next
owner is changed. The Clap conversion is isolated because it has the largest
CLI regression surface. Public DTO hard cuts, if selected, are isolated from
behavior-preserving internal changes so downstream breakage is obvious.

## Validation Gates

Every slice runs formatting and focused unit/public-API tests. Changes touching
feature-gated library code also run no-default and host checks. Changes touching
CLI grammar run affected command tests and CLI smoke coverage. Cache lifecycle
changes run the relevant corrupt/missing/partial-failure fixtures before broader
Clippy. The narrow Subnet catalog slice additionally compiles and tests with
only `subnet-catalog-host` enabled and verifies that Reqwest and CBOR are absent
from that feature graph.

Before handoff for release, run workspace all-target/all-feature Clippy, the
library process-boundary guard, public documentation checks, formatting checks,
and the release guards appropriate to a prepared but unversioned worktree. Do
not run version bumps, commits, tags, pushes, publishing, or release targets.

## Non-Goals

- adding reporting commands or new network calls;
- changing report JSON or cache schemas merely to reduce Rust field repetition;
- merging all authority requests, provenance, sources, or errors;
- replacing typed follow-up reports with dynamic Candid invocation;
- silently migrating or reading obsolete cache formats;
- deleting tests solely to lower the test count;
- broad workspace restructuring unrelated to an identified shared owner.
