# 0.34 Design: CloudEngine Provider Reporting

## Status

- Status: implemented for the 0.34 release slice
- Authority: official IC Dashboard v3 node-provider resources
- Collection mode: one response-bounded live REST request
- Public family: `ic_query::cloud_engine`

## Purpose

The native CloudEngine control plane exposes Subnet bindings, operator
settings, and marketplace prices, but it does not expose a complete provider
directory. The official Dashboard node-provider resource now carries explicit
CloudEngine node, engine, unassigned-node, and location fields alongside each
NNS node provider. This capability remains top-level CloudEngine product
surface while preserving Dashboard as the data authority.

```bash
icq cloud-engine provider list
icq cloud-engine provider info <node-provider-id>
```

The target is an NNS node-provider principal. It is not a CloudEngine Subnet,
operator canister, engine canister, data center, or individual node.

## Collection Contract

The built-in provider source is another capability on `LiveIcSource`, the
existing official Dashboard adapter. `list` requests `/node-providers` once;
`info` canonicalizes its target and requests `/node-providers/{principal}`
once. Both use the shared credential-free HTTP(S) endpoint validation,
redirect rejection, synchronous runtime boundary, and 8 MiB response ceiling.

The complete list admits at most 1,000 source rows and each general or
CloudEngine location array admits at most 100 rows. List construction validates
the complete resource before filtering and sorts retained providers by
canonical principal. A row is retained when any explicit CloudEngine count is
nonzero or its CloudEngine location set is nonempty.

Exact info does not apply that filter. A valid provider with zero current
CloudEngine fields is returned with `cloud_engine_evidence_present: false`, so
absence of evidence is not confused with an unknown provider.

## Report Contract

Schema-1 reports flatten `IcDashboardReportProvenance` and preserve the raw
Dashboard provider contract:

- canonical provider principal, display name, optional website, and nullable
  logo URL;
- independently declared ordinary-node and CloudEngine location counts plus
  each raw data-center key, label, owner, region, latitude, and longitude; and
- general node, unassigned-node, rewardable-node, allowance, and Subnet counts
  plus CloudEngine node, unassigned-node, and engine counts.

The list additionally reports the complete source provider count and retained
CloudEngine provider count. JSON preserves raw numeric and optional fields;
text gives a compact provider table or an exact provider summary followed by a
separate CloudEngine-location table.

Projection rejects empty or oversized resources, duplicate or noncanonical
principals, blank/oversized/control-bearing labels, mismatched declared
location counts, duplicate data-center keys, nonfinite or out-of-range
coordinates, and unassigned totals above their corresponding node totals.
Ordinary-node and CloudEngine location arrays are not required to overlap: the
live API exposes them as parallel scopes and some CloudEngine footprint exists
only in the CloudEngine array.

## Authority Limits

Reports state `authority: official_ic_dashboard_api`, `certified: false`, and
`point_in_time_guaranteed: false`. Dashboard provider counts are off-chain
observations. They are not promoted to Registry state or native control-plane
evidence and do not prove health, reachability, assignment, ownership of an
operator canister, or one coherent snapshot across other reports.

The v3 boundary-node-location resource cannot enrich provider rows safely. It
contains only aggregate location buckets and node counts, without individual
node or provider identifiers. No positional, name-based, or geographic join is
attempted.

## Public Library Boundary

Pure no-default builds expose provider requests, reports, rows, locations,
bounds, and text renderers from `ic_query::cloud_engine`. `dashboard-host`
adds `CloudEngineProviderSource`, its source-data DTOs, live/custom-source
builders, and the implementation on `LiveIcSource`.

The separate `cloud-engine-host` feature continues to own native canister
queries through `LiveCloudEngineSource`. Neither focused feature implicitly
enables the other; the convenience `host` feature includes both.

## Cache Contract

Both operations are live-only and make one finite request. They do not read,
write, invalidate, or migrate a cache. Adding persistence would require a
separate freshness and complete-snapshot policy that this release does not
need.
