# 0.36 Design: Node-Provider Reward Reporting

- Status: implemented for the 0.36 release slice
- Scope: exact reward detail, one bounded reward page, and bounded aggregate
  reward history
- Authority: official IC Dashboard REST API
- Persistence: none

## User contract

Node-provider identity remains under the existing NNS entity namespace, while
the report clearly attributes reward records to the Dashboard:

```bash
icq nns node-provider reward info 7562
icq nns node-provider reward list --limit 25
icq nns node-provider reward history --start 1752537600 --end 1784073600 --step 86400
```

Every operation is a live, one-request report. It neither reads nor writes a
cache. The source is off-chain and non-certified, and the reports do not claim
one point-in-time view across Dashboard records or native NNS Governance.

## Exact detail

`reward info` requests `/reward-node-providers/{id}` for one numeric Dashboard
record id. It does not scan the collection or fall back to Governance. A
successful source response must echo the exact requested id.

The public row retains:

- raw reward amount in ICP e8s;
- canonical node-provider principal;
- raw reward-mode name and mode-specific details JSON object;
- reward time as Unix seconds and the separate raw Dashboard update string;
- optional proposal id and Registry version;
- optional maximum reward and minimum XDR floor inputs; and
- optional XDR conversion timestamp in Unix seconds and raw
  XDR-permyriad-per-ICP value.

Reward mode is deliberately text, not a closed enum. Mode-specific details are
an object instead of a `RewardToAccount`-only DTO so current and additive modes
remain visible without discarding their evidence. A present `to_account` value
is still checked as a 32-byte lowercase hexadecimal account identifier.

## One-page list and overlap evidence

`reward list` requests `/reward-node-providers` exactly once. It accepts:

- `limit` from 1 through 100, default 50;
- a zero-based `offset`; and
- optional `max_reward_node_provider_index`, exposed as
  `max_reward_index`/`--max-reward-index`.

The Dashboard's reported maximum index is not the same identity as each
record's `id`. Both remain distinct fields.

Live audit requests found overlapping ids across adjacent offsets, including
when both requests reused the same maximum reward index. The adapter therefore:

- preserves the source page order;
- validates uniqueness only within one response;
- never automatically follows, merges, or deduplicates pages;
- reports `pages_may_overlap: true`; and
- exposes only an arithmetic `next_offset_hint`.

API exhaustion, completeness, and stable snapshot membership are not claimed.

## Aggregate history

`reward history` requests `/timeseries/reward-node-providers` exactly once with
inclusive `start`, inclusive `end`, and `step` Unix-second parameters. The
default is 365 days ending at collection time with an 86,400-second step.
Accepted steps match the documented 60 through 259,200-second range, and the
inclusive request is limited to 1,000 possible observations.

The upstream tuple is amount first and timestamp second. The public report
names both fields and stores them as `amount_e8s` and `timestamp_unix_secs`.
Observations must be within the requested window and strictly increasing by
timestamp.

## Historical numeric shapes

Older detail rows expose some optional integer identifiers as JSON numbers
with a zero decimal suffix, while history tuples may also be encoded as JSON
floating-number tokens. The wire boundary converts a value to `u64` only if it
is an unsigned integer or has a decimal fraction containing only zeroes.
Decimal-encoded values must also remain within JSON's exact integer range. It
rejects negative, fractional, or unsafe values instead of accepting a lossy
float conversion.

## Provenance and schema

All three reports flatten the shared Dashboard provenance:

- schema version `1`;
- network `ic`;
- authority `official_ic_dashboard_api`;
- exact source endpoint, collection time, and collector;
- `certified: false`; and
- `point_in_time_guaranteed: false`.

This is a pre-1.0 hard-cut schema-1 contract. There is no compatibility alias,
fallback reader, migration, or persisted schema.

## Ownership

- CLI parsing and dispatch live under `ic-query-cli`'s NNS node-provider
  namespace.
- Request/report/source-data DTOs live in the IC Dashboard model because the
  Dashboard is the data authority.
- The focused source module owns bounds, validation, and report projection.
- The live module owns URL and wire conversion.
- Text rendering is separate; JSON preserves raw script-friendly values.

## Explicit exclusions

This slice does not:

- enumerate or mutate native Governance reward state;
- claim stable pagination or complete reward history from offset pages;
- join reward records to cached Registry node-provider metadata;
- convert e8s to display ICP or XDR values;
- parse the raw Dashboard database update string into a second timestamp; or
- create a reward cache.

## Verification

Fixture tests cover request-before-source validation, exact identity, page
metadata, duplicate rejection, history order/window checks, historical
integer-valued JSON numbers, text/JSON rendering, CLI options, namespace help,
and public Rust API exposure. Live smoke verification uses one exact current
record, one two-row page, and one short aggregate history window.
