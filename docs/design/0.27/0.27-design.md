# ic-query 0.27 Design: Bounded Official ICRC Analytics

## Status

- Status: implemented
- Last reviewed: 2026-08-04
- Scope: bounded, live-only total-supply and token-value history plus scalar
  indexed counts from the official IC Dashboard ICRC API

## Goal

Add useful historical ICRC analytics without enumerating ledger blocks,
accounts, holders, or transactions and without presenting off-chain Dashboard
data as certified ledger state.

The reports are deliberately narrow:

```bash
icq icrc analytics account count mxzaz-hqaaa-aaaar-qaada-cai
icq icrc analytics holder count mxzaz-hqaaa-aaaar-qaada-cai
icq icrc analytics token-values mxzaz-hqaaa-aaaar-qaada-cai
icq icrc analytics total-supply mxzaz-hqaaa-aaaar-qaada-cai
icq icrc analytics transaction count mxzaz-hqaaa-aaaar-qaada-cai
```

The series operations retrieve one explicitly bounded total-supply or external
token-value range for one canonical ledger canister principal. Each count
operation retrieves only the current number of accounts, holders, or
transactions indexed for that ledger. Every operation makes exactly one HTTP
request, follows no cursor, performs no per-row lookup, and reads or writes no
cache.

## Authority

The source is the official IC Dashboard ICRC API, not the ledger canister:

- base endpoint: `https://icrc-api.internetcomputer.org/api/v2`;
- resource:
  `/ledgers/{ledger_canister_id}/total-supply`;
- response: `data` containing `[timestamp, raw_value]` pairs; and
- token-value resource:
  `/ledgers/{ledger_canister_id}/token-values`;
- token-value response: echoed ledger principal plus raw nullable price,
  24-hour volume, provider, provider-URL, and timestamp fields; and
- scalar count resources:
  `/ledgers/{ledger_canister_id}/{accounts|holders|transactions}/count`;
- scalar count response: `total` as one non-negative integer; and
- OpenAPI document reviewed on 2026-08-04 with SHA-256
  `dce5d15804d8a75f8ccf71deab6438273d62e9780da1cd9070723123873e482c`.

The report uses the existing `IcDashboardReportProvenance` contract:

- `authority: official_ic_dashboard_api`;
- `network: ic`;
- `certified: false`;
- `point_in_time_guaranteed: false`;
- exact source endpoint and retrieval timestamp.

An accepted ledger principal is only a requested identity. The API indexes a
curated set of ledgers and may reject or have no data for another valid ICRC
ledger. `ic-query` must preserve that HTTP failure rather than claiming the
analytics service covers every arbitrary ICRC ledger.

The existing native `icq icrc ledger token` report remains the direct source
for current `icrc1_total_supply`. The analytics report does not replace,
reconcile, or elevate its historical off-chain values to native ledger
authority.

Account, holder, and transaction counts are likewise the Dashboard index's
current derived totals. They are not certified ledger values, point-in-time
snapshots, or evidence that every ledger record has been indexed. The
operations intentionally do not request the rows behind those counts. Account
and holder remain distinct native API classifications; `ic-query` does not
infer that every indexed account is a current holder.

Token-value rows have two levels of provenance. The report records the
official Dashboard API as the aggregation authority, while every row preserves
the external provider name and URL returned by that API. Neither level is
certified IC state, and `ic-query` does not endorse, reconcile, normalize, or
verify the external market values. The legacy `price`/`volume_24h` fields and
explicit `price_usd`/`volume_24h_usd` fields remain separate raw strings.

## Request Bounds

The public query contains inclusive `start_unix_secs`, inclusive
`end_unix_secs`, and raw `step_secs`. The only supported steps are the two
values in the reviewed API contract:

- `3600` for hourly observations; and
- `86400` for daily observations.

CLI defaults are:

- end: current Unix time;
- start: 30 days before end, clamped to the API minimum for an explicitly
  early end; and
- step: `86400`.

Before constructing the live request, the library requires:

- a canonical ledger canister principal;
- start at or after the API minimum `1620328530`;
- end greater than or equal to start;
- end no later than the caller-supplied collection time;
- one supported step; and
- `(end - start) / step + 1 <= 1000` requested observations.

The live source applies the same query validation before URL construction.
A custom source receives the normalized canonical ledger principal and exact
query.

The scalar count operations expose no pagination, limit, cursor, filter, or
implicit follow-up input. Although the account and transaction endpoints
accept optional filters, this release deliberately requests only the
unfiltered ledger total. `IcIcrcIndexedCountRequest` pairs one typed
`Account`, `Holder`, or `Transaction` kind with the same canonical ledger,
endpoint, and collection-time target as total supply.

Token-value requests contain explicit `start_unix_secs`, `end_unix_secs`, and
an explicit row `limit`. The CLI defaults to the preceding
24 hours and 1,000 rows. The library requires:

- end greater than or equal to start;
- end no later than the caller-supplied collection time;
- a window no larger than the official API's 90-day cap; and
- a limit from 1 through the stricter `ic-query` ceiling of 1,000 rows.

The upstream endpoint permits 5,000 rows. The lower local ceiling keeps one
response small and consistent with the other analytics surfaces. Reaching the
requested limit produces `limit_reached: true`; it never becomes a claim that
the requested range was completely represented.

Every `LiveIcSource` request also passes through the shared Dashboard transport
ceiling of 8 MiB. A declared oversized body is rejected before body-collection
allocation or consumption, while streamed bytes enforce the same ceiling for
chunked or unknown-length responses. This transport bound precedes JSON
decoding and does not add caching, pagination, retries, or follow-up calls.

## Source And Projection Contract

`IcIcrcAnalyticsSource` is a focused capability implemented by the existing
`LiveIcSource`. `IcIcrcAnalyticsRequest` owns the shared endpoint, collection
time, and ledger identity for every operation. This keeps official REST
analytics on the Dashboard adapter instead of mixing them into the native
`LiveIcrcSource` canister adapter or introducing one concrete live adapter for
one report.

Source data must echo:

- the exact shared source request;
- the canonical requested ledger principal; and
- the exact bounded total-supply query.

Projection validates that:

- returned observation count does not exceed the requested bound or 1,000;
- every timestamp lies inside the requested inclusive window;
- timestamps are strictly increasing and unique; and
- every total-supply value is nonempty canonical unsigned decimal text.

Rows preserve the raw base-unit value as a string. The report does not infer
token decimals, format token units, fill missing intervals, interpolate
values, or calculate mint and burn attribution. Those would require another
authority or additional requests.

Indexed-count source data must echo the exact shared source request, canonical
ledger principal, and requested count kind. Projection preserves the returned
`u64` total and the same flattened Dashboard provenance; it does not fetch,
sample, or infer account, holder, or transaction rows.

Token-value source data must echo the exact shared source request, canonical
ledger principal, and requested query. Projection rejects more rows than the
requested or local limit, a missing timestamp, a timestamp outside the
requested window, or decreasing timestamp order. Equal timestamps remain
valid because distinct external providers may report at the same second. All
other nullable fields are preserved without lossy parsing or field merging.

## CLI Ownership

The command lives below `icq icrc analytics` because users discover it by the
ICRC subject. Help and report provenance explicitly identify its separate
official Dashboard authority. The library types remain under `ic_query::ic`
because `LiveIcSource` owns official REST transport and provenance.

`icq icrc analytics total-supply` accepts:

- one ledger canister principal;
- optional `--start`, `--end`, and `--step` bounds;
- `--source-endpoint`; and
- `--json`.

`icq icrc analytics account|holder|transaction count` accepts the same ledger
principal, `--source-endpoint`, and `--json` target options but no series,
filter, or pagination controls. All three commands share one typed library
request/report/source path and one CLI dispatch path.

`icq icrc analytics token-values` accepts the ledger principal,
`--source-endpoint`, `--start`, `--end`, `--limit`, and `--json`. It does not
offer a cursor or refresh option because the operation is one bounded live
request and owns no cache.

It rejects the global `--network` option like every endpoint-identified
Dashboard and ICRC command. Text is a human-facing raw series; JSON retains
the exact principal, bounds, provenance, counts, timestamps, base-unit supply
strings, and raw market strings.

## Non-Goals

- current total supply already available from `icrc1_total_supply`;
- circulating-supply policy or pre-swap account classification;
- account, holder, or transaction enumeration beyond the scalar counts;
- filtered account or transaction counts;
- transaction or block crawling;
- implicit pagination or automatic follow-up calls;
- mint, burn, fee, or transaction-volume attribution;
- market-value reconciliation, provider endorsement, currency conversion, or
  native-ledger verification of external token values;
- support claims for ledgers not indexed by the Dashboard API;
- certification or point-in-time guarantees;
- caching; and
- compatibility aliases for another command or report shape.

## Validation

Targeted tests cover:

- request bounds before source invocation;
- canonical ledger identity and exact source query matching;
- ordered, unique, in-window rows and canonical raw values;
- returned-row bounds;
- live URL construction and wire decoding;
- every indexed-count kind, identity/provenance/kind validation, and one-call
  URL/wire decoding;
- token-value time/row bounds, exact source echo, nullable raw-field
  preservation, timestamp ordering, missing timestamp rejection, and explicit
  limit-reached evidence;
- exact-limit, declared-oversize, chunked-oversize, truncated-body, and invalid
  JSON behavior at the shared Dashboard transport boundary;
- public host and no-default DTO surfaces;
- CLI defaults, explicit bounds, JSON, help, network rejection, namespace
  help, and alphabetical command ordering; and
- renderer provenance and raw base-unit values.
