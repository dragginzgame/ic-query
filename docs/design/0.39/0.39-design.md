# 0.39 Design: Portable NNS Proposal Activity Analytics

- Status: implemented through the 0.39.1 release slice
- Initial scope: deterministic activity counts over one caller-supplied,
  API-exhausted NNS proposal collection
- Authority: local projection of retained NNS Governance proposal evidence
- Runtime: pure Rust under the existing no-default library surface
- Persistence: caller-owned; no new cache or stable-memory contract
- Workspace: exactly the existing `ic-query` and `ic-query-cli` crates

## Purpose

The 0.38 release made bounded and resumable NNS proposal collection available
to native and canister callers through one shared library boundary. A caller
can now retain every admitted page and observe Governance API exhaustion, but
it must still write its own validation and aggregation code before presenting
basic governance activity in a dashboard.

The first 0.39 slice adds that reusable pure projection. It summarizes the
proposal evidence already held by the caller without making another network
call, selecting a runtime, reading a filesystem cache, or prescribing how the
caller stores the collection.

The scope is deliberately proposal activity rather than a broad “governance
health” score. Counts by native topic, decision status, reward status, and UTC
proposal day are factual projections of retained rows. Participation quality,
decentralization, voting-power concentration, policy impact, and reward
fairness require additional definitions and authority and are not inferred.

## Release outcome

The initial public library surface consists of:

- `NNS_PROPOSAL_ACTIVITY_REPORT_SCHEMA_VERSION`, fixed at `1` before 1.0;
- `NnsProposalActivityRequest`, containing an optional half-open proposal-time
  window;
- `build_nns_proposal_activity_report`, a synchronous pure builder over a
  complete `NnsProposalCollectionState` and borrowed proposal rows;
- `NnsProposalActivityReport` and typed count rows for topic, status, reward
  status, and UTC day;
- `NnsProposalActivityError`, retaining deterministic input or accounting
  failures;
- `validate_nns_proposal_activity_report` and
  `NnsProposalActivityValidationError`, providing pure validation for retained
  or deserialized schema-1 reports; and
- `nns_proposal_activity_report_text`, the reusable human-facing renderer.

The builder is available with `default-features = false` on native and Wasm
targets. The 0.39 release adds no CLI command or option.

## Crate and feature boundary

The workspace remains two crates:

```text
ic-query
  proposal collection state and rows
  pure proposal activity validation, aggregation, report model, and renderer

ic-query-cli
  unchanged; no 0.39.0 parsing, dispatch, or process output
```

No new Cargo feature is introduced. The analytics builder belongs to the base
`ic-query` surface because it needs only existing public DTOs, Serde, and the
standard library. It must not enable `canister`, `host`, `nns-host`, Tokio,
`ic-agent`, Reqwest, filesystem capabilities, or another dependency.

There is no Wasm-specific analytics implementation. Native processes,
canisters, browser Wasm, fixture tests, and offline tools call the same pure
function. The existing `canister` feature remains relevant only when a caller
chooses to collect the input through `CanisterNnsSource`.

## Input contract

The builder borrows three inputs:

```rust,ignore
pub fn build_nns_proposal_activity_report(
    request: &NnsProposalActivityRequest,
    collection: &NnsProposalCollectionState,
    proposals: &[NnsProposalRow],
) -> Result<NnsProposalActivityReport, NnsProposalActivityError>;
```

`collection` must be a valid final state whose status is `complete`. A
`ready`, `collecting`, or `page_limit_reached` state is rejected. In
particular, a page-limit stop is useful progress but cannot support complete
counts.

The input row count must exactly equal `collection.proposals_fetched()`. Every
row must have a nonzero proposal id and proposal timestamp, and ids must be
unique across the complete slice. The typed topic, status, and reward-status
classifications must equal the result of applying their public `from_code`
functions to the raw native codes. Input order is not significant; callers do
not need to reorder retained pages before analysis.

The builder revalidates deserialized collection state through the existing
collection invariant path. The internal validator should be shared with the
continuation engine rather than copied or exposed through a compatibility
wrapper.

The builder does not prove that caller-owned rows historically came from the
state supplied beside them. The collection state contains accounting and
provenance, not an authenticated content commitment, and both values may have
been modified by their owner. Structural validation catches accidental
mismatches; it does not turn caller storage into certified evidence.

## Completeness and authority

“Complete” means the retained walk observed `list_proposals` API exhaustion
under the 0.38 continuation contract. It does not mean:

- all proposals that have ever existed outside the API's retained surface;
- proposals hidden from the collecting principal by Governance visibility;
- one atomic Governance snapshot;
- certified response content; or
- a collection cryptographically bound to a Registry version.

Sequential proposal pages can span Governance changes. Open proposals can
change status or tally while collection proceeds, and no source version pins
the walk. Every activity report therefore sets
`point_in_time_guaranteed: false`; this is not a caller-selectable field.

The report retains the final collection state's network, fixed Governance
canister id, concrete source provenance, caller-supplied collection start and
update times, page count, and total admitted row count. Replica-query and
replicated inter-canister provenance remain distinct. Local derivation does
not strengthen either transport's assurance.

## Time-window contract

`NnsProposalActivityRequest` contains:

- `from_proposal_timestamp_seconds: Option<u64>`, inclusive; and
- `until_proposal_timestamp_seconds: Option<u64>`, exclusive.

When both are present, `from` must be strictly less than `until`. The bounds
apply only to `proposal_timestamp_seconds`; they do not select by deadline,
decision, execution, failure, tally, or reward-settlement time.

The time window is a local view over an already complete input. It never
changes collection identity, authorizes an early pagination stop, or implies
that proposal ids are timestamp ordered. The report records both requested
bounds, the included row count, rows excluded before `from`, and rows excluded
at or after `until`.

An unbounded request includes every supplied row. A valid window with no
matching proposals succeeds with empty count tables and absent earliest/latest
included timestamps.

## Report contract

The schema-1 `NnsProposalActivityReport` contains:

| Field group | Evidence |
| --- | --- |
| collection | network, Governance canister id, concrete source provenance, collection start/update times, admitted pages and proposals |
| assurance | `point_in_time_guaranteed: false` |
| selection | inclusive `from`, exclusive `until`, included count, and two exclusion counts |
| observed range | optional earliest and latest included proposal timestamps |
| dimensions | canonically ordered topic, status, reward-status, and UTC-day count rows |

The report schema version is `1`. Before 1.0, a breaking report-shape change
replaces schema 1 in place; it does not introduce schema 2, a legacy reader,
or a migration.

Dimension rows preserve raw evidence:

```rust,ignore
pub struct NnsProposalTopicCount {
    pub topic: i32,
    pub topic_text: NnsProposalTopic,
    pub proposal_count: u64,
}

pub struct NnsProposalStatusCount {
    pub status: i32,
    pub status_text: NnsProposalStatus,
    pub proposal_count: u64,
}

pub struct NnsProposalRewardStatusCount {
    pub reward_status: i32,
    pub reward_status_text: NnsProposalRewardStatus,
    pub proposal_count: u64,
}

pub struct NnsProposalDayCount {
    pub day_start_timestamp_seconds: u64,
    pub proposal_count: u64,
}
```

Topic, status, and reward-status rows sort by raw numeric code. Distinct
unrecognized codes remain distinct rows even when their typed classification
is `Unspecified`. Day rows sort by ascending UTC day start, calculated with
integer division by 86,400. JSON retains raw Unix seconds; text rendering may
format the day for people.

Every dimension count sums exactly to `included_proposal_count`. Empty groups
are omitted rather than padded with every known enum value. Report counts use
`u64` and all increments and conversions are checked.

### Retained report validation

`validate_nns_proposal_activity_report` accepts a borrowed report and performs
no live host call or state write. It is intended for reports restored from
caller-owned stable memory, a database, a file, or an application message.
Freshly built reports pass through the same validator before the builder
returns them.

The validator checks schema 1, the mainnet network and Governance canister,
transport-specific source provenance, nonzero complete-collection page
evidence, and the mandatory false point-in-time guarantee. It rechecks the
half-open time window; included and excluded count accounting; included range
presence, order, and bounds; raw-code classification and strict ordering;
nonzero row counts and per-dimension totals; and UTC-day alignment, ordering,
and coverage of the included timestamp endpoints.

The retained report contains aggregate evidence rather than its source rows.
Validation can therefore prove internal consistency and canonical shape, but
cannot recompute the aggregates, authenticate caller storage, or establish a
cryptographic link to the original collection.

## Deliberately excluded calculations

The initial report does not aggregate:

- ballots or distinct voting neurons;
- yes/no voting power, turnout, or adoption percentages;
- total potential voting power;
- proposal reject costs;
- proposer rankings;
- action labels or free-text content;
- reward amounts or reward-event history; or
- public-neuron stake, voting power, dissolve state, or recent ballots.

Summing ballot or voting-power values across proposals would combine different
electorates and observation times. Recent ballots on public-neuron rows are a
bounded, visibility-dependent view rather than complete delegation or
participation history. Public neuron fields are also collected sequentially
and cannot support a truthful network-wide point-in-time balance. Those inputs
remain available to callers, but 0.39.0 does not assign them broader meaning.

## Determinism and resource bounds

For identical request, collection state, and rows, the serialized report is
byte-order deterministic after ordinary Serde field ordering. Input order must
not affect the result. Dimension rows use the canonical ordering above rather
than hash-map iteration order.

The builder:

- makes zero network calls;
- performs one linear pass over input rows plus deterministic ordering of the
  bounded distinct dimension sets;
- borrows and never clones the full input collection;
- allocates only uniqueness tracking and aggregate rows;
- performs no retry, scheduling, state write, or background work; and
- returns accounting overflow as a typed error.

The number of topic, status, and reward-status rows is bounded by the distinct
raw codes present. The number of day rows is at most the included proposal
count. No caller-configured output limit is needed because the report cannot
have greater cardinality than its already retained input.

## Text and JSON output

JSON is the authoritative script-friendly projection. It retains raw codes,
Unix seconds, counts, provenance, and the false point-in-time guarantee.
Human text renders a provenance and selection preamble, one blank line, then
separate titled tables for topic, status, reward status, and daily activity.
Empty tables are reported as empty sections rather than silently omitted.

The library renderer returns `String`. It does not inspect a terminal, select
stdout or stderr, print progress, or write process output.

## Error contract

`NnsProposalActivityError` keeps aggregate failures separate from transport
and cache failures. It distinguishes at least:

- invalid or inconsistent collection state;
- collection not complete, retaining its current status;
- invalid half-open time bounds;
- supplied row-count mismatch;
- missing, zero, or duplicate proposal ids, or a zero proposal timestamp;
- raw/typed topic, status, or reward-status mismatch; and
- count or platform-width conversion overflow.

Validation fails before publishing a partial report. There is no best-effort
mode that silently drops malformed rows.

`NnsProposalActivityValidationError` separately represents a structurally or
semantically invalid retained report. Its deterministic reason covers the
first failed report invariant. The validator does not accept a legacy schema
or repair malformed values.

## Module ownership

The proposal report family continues to own the feature:

- proposal activity request/report/count DTOs, validation, aggregation, and
  text rendering live under `crates/ic-query/src/nns/proposals/report/`;
- the existing collection module owns continuation-state invariants;
- reusable UTC formatting remains in the existing shared time helper;
- public re-exports remain under `ic_query::nns::proposals`; and
- `ic-query-cli` receives no 0.39.0 code.

No generic analytics framework, universal grouping trait, dataframe layer, or
cross-authority report abstraction is introduced. Small proposal-specific
helpers are preferable until another report demonstrates a genuinely shared
contract.

## Cache and publication policy

The builder reads no cache and writes no report. A native caller may supply
rows it obtained through the same continuation API; a canister may supply rows
from its own stable state; and a test may supply fixtures. Those storage paths
remain outside the analytics contract.

The report is an ordinary Serde value. Callers decide whether to serve it
immediately, persist it, replace an older report atomically, or recompute it.
The library adds no cache key, freshness default, stable-memory layout, lock,
attempt sidecar, or scheduler. A caller restoring a persisted report should
run `validate_nns_proposal_activity_report` before publishing or using it.

## Verification

Tests cover:

- complete unbounded aggregation across every dimension;
- inclusive `from` and exclusive `until` boundaries;
- empty valid windows;
- distinct unknown raw codes and canonical row ordering;
- identical output from permuted input order;
- incomplete and page-limited state rejection;
- deserialized state revalidation and state/row-count mismatch;
- missing, zero, duplicate, and classification-inconsistent rows;
- checked count conversion and UTC-day boundary bucketing;
- exact text section separation and raw JSON fields;
- serialized activity report round-trip validation;
- retained-report schema, identity, source, assurance, window, accounting,
  range, classification, ordering, count-total, and UTC-day corruption;
- no-default and public downstream API construction; and
- `wasm32-unknown-unknown` checks with no features and with `canister`.

The implementation gate includes the repository feature-boundary, public-doc,
schema-version, Clippy, and full workspace test checks.

## Explicit exclusions

The 0.39.0 slice does not:

- add a crate, Cargo feature, CLI command, or option;
- make a Governance, Registry, Dashboard, ledger, or other network call;
- accept partial proposal collection as complete analytics;
- add a filesystem cache or stable-memory policy;
- join proposal rows to neuron, Registry, or off-chain data;
- infer delegation, owner state, reward history, turnout quality, policy
  impact, decentralization, or governance health;
- claim certification, historical completeness, or point-in-time consistency;
  or
- retain a compatibility surface for a replaced pre-1.0 contract.

## Later work after 0.39.0

Additional proposal dimensions should be added only when their semantics are
factual and their output cardinality remains explicit. Native reward history,
delegation/followee state, and authenticated owner views require their own
authority and visibility designs rather than derivation from public proposal
or neuron rows.

Public-neuron distribution reports require a separate decision about how to
present sequential, visibility-limited current values without implying an
atomic network snapshot. They are not part of this initial activity report.
