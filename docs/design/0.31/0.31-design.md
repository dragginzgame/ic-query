# 0.31 Design: Public CloudEngine Reporting

## Status

- Status: implemented for the 0.31 release slice and schema-1 cleanup follow-up
- Upstream contract: ICP CLI 1.3.0 CloudEngine integration
- Authority: versioned NNS Registry inventory plus mainnet CloudEngine control-plane bindings/details
- Canister: `q6cfj-fyaaa-aaaar-qb77q-cai`
- Collection mode: bounded live direct reports; cache-backed Registry inventory plus bounded live bindings for list

## Purpose

ICP CLI 1.3.0 made the public CloudEngine control plane a concrete upstream
surface by adding Subnet-to-engine-operator resolution. `ic-query` adopts that
read-only contract as its own top-level authority family:

```bash
icq cloud-engine list
icq cloud-engine info <subnet-id>
icq cloud-engine prices
```

CloudEngine is not nested under `icq nns`, `icq ic`, or `icq system`. The
control-plane canister and per-engine operator canisters are their own
authority, and the top-level family keeps that provenance visible.

## Report contracts

`cloud-engine list` loads the complete set of Subnets classified as
`cloud_engine` by the versioned Registry Subnet Catalog. It then attempts one
exact `getEngineOperatorBySubnet` query for each returned Subnet, with a hard
cap of 100 rows. The report does not call operator canisters for owners,
administrators, Caffeine settings, domains, canister inventories, status, or
metrics; those public operator details remain an explicit `info` target.
Control-plane inventory methods are identity- or administrator-scoped rather
than a public anonymous complete-inventory contract, so they do not define the
row universe for this command.

The list report keeps each authority in a separate field group. Registry
version, assurance, source endpoints, query count, catalog digest, cache
disposition, timestamp, and classification provenance describe the inventory.
The fixed control-plane canister, endpoint, observation timestamp, collector,
and uncertified consistency flags describe only the binding lookups. Rows use
separate `resolved`, `absent`, and `failed` outcomes so a query failure cannot
be confused with a successful absent response or erase the Registry row.

`cloud-engine info` first calls `getEngineOperatorBySubnet` on the fixed
control-plane canister. An absent binding is a successful, explicit one-call
result; it does not prove that the Subnet or engine exists. When an operator
exists, the command makes four public follow-up queries on that operator
canister:

- `getEngineOwner`;
- `getPlatformAdmin`;
- `getCaffeineSettings`; and
- `listDomains`.

The report preserves the requested Subnet principal, operator-binding presence
and canister principal, optional owner and platform-admin principals,
optional Caffeine setting, and a sorted optional domain list. It makes one or
five native query calls and never enumerates other CloudEngine Subnets.

`cloud-engine prices` calls `getNetworkFee` and `listMarketplacePrices` on the
control-plane canister. It accepts at most 1,000 rows, sorts them by the native
marketplace key, and preserves:

- the raw finite non-negative network-fee fraction;
- node type, optional data-center id, and optional provider principal;
- exact net and gross monthly cycle counts as arbitrary-precision decimal
  strings, accepted up to 256 digits per field; and
- the raw signed Unix-nanosecond update timestamp.

The builder checks that every flattened key matches its structured identity,
that decimal cycle strings are canonical, gross is not less than net, and row
keys are unique. Text formats cycle counts for people; JSON retains the raw
decimal strings.

## Authority and consistency

Direct reports record schema version 1, network, fixed control-plane principal,
replica endpoint, collection timestamp, collector identity, and exact query
call count. They state:

```text
authority: cloud_engine_control_plane_canister
certified: false
point_in_time_guaranteed: false
```

These are ordinary canister query responses. A successful transport response
does not authenticate application data through a certificate/witness contract,
and sequential operator calls may observe different states. The reports do not
inherit a Registry version or the official Dashboard's off-chain authority.

The built-in source and custom-source builders support only the mainnet `ic`
network and reject another identity before endpoint construction or source
invocation. The endpoint remains explicit through `--source-endpoint`.

## Boundedness and feature boundary

The direct `info` and `prices` commands do not read or write a report cache.
Operator detail is exact-target and bounded to five calls; marketplace
collection is bounded to two calls and 1,000 rows. Claimed domains are capped
at 100. `list` uses the existing complete Subnet Catalog cache and its explicit
missing-or-invalid refresh policy, then attempts exactly one control-plane
binding query for each of at most 100 Registry rows. Per-row failures remain
visible in the completed report.

The pure report DTOs and renderers remain available without host dependencies.
The focused `cloud-engine-host` feature enables only `ic-agent`, Tokio, and URL
validation directly. It does not directly enable cache filesystems, Registry
Prost decoding, Futures fan-out, Reqwest REST transport, CBOR certification, or
SHA-256 support. The joined list API is available when
`subnet-catalog-host` is also selected; `host` includes both focused features.

## Audit decisions and remaining opportunities

The 0.31 audit deliberately excludes CloudEngine mutation and administrative
methods, arbitrary Candid invocation, private operator state, unbounded
operator-detail fan-out, hidden caching, and joins that would falsely imply one
point-in-time authority.

Useful later slices are:

1. extend observed node health to CloudEngine nodes when an official bounded
   Dashboard resource exposes that scope truthfully; and
2. add bounded domain or operator operational evidence only when the public
   interface supplies a stable read-only contract.

The repository audit also confirmed pre-existing schema identifiers above 1
in the Subnet Catalog and certified Registry report/archive surfaces. The
separate 0.31.1 cleanup hard-cuts the current Registry-version report,
certified-delta report, archive manifest, ordinary Subnet Catalog, and its
list/info/refresh reports back to schema 1. Existing content with another
identifier is rejected by the exact-version readers; there is no fallback,
migration, or dual parser. This keeps the evidence/cache contract change
separate from the initial CloudEngine implementation.
