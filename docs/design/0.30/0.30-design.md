# 0.30 Certified Registry Evidence

## Status

- State: `0.30.1` certified latest-version and bounded single-delta-batch
  foundations implemented; replay and catalog publication remain planned
- Last reviewed: 2026-08-05
- Scope: bounded authenticated Registry evidence without overstating ordinary
  query assurance
- CLI grammar: unchanged

## Goal

`0.30` establishes a cryptographically authenticated path from the mainnet IC
root key to Registry evidence. The work proceeds in independently useful
stages: first authenticate the Registry's latest version, then validate
certified delta batches, then reconstruct and publish a certified Subnet
Catalog only if bootstrap and incremental replay remain explicitly bounded.

The release must preserve the distinction between:

- a certified `current_version` leaf;
- an exact-version ordinary `get_value` join;
- matching ordinary evidence from multiple endpoints; and
- Registry key state reconstructed from a complete certified delta sequence.

Only the final case may produce `CatalogAssurance::Certified`.

## Upstream Contract

The implementation follows the pinned Registry canister implementation and
protobuf definitions reviewed for this design:

- [Registry certified query methods](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/canister/canister/canister.rs)
- [Registry certification tree](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/canister/src/certification.rs)
- [Registry transport protobuf](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/transport/proto/ic_registry_transport/pb/v1/transport.proto)
- [Mixed hash-tree protobuf](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/protobuf/def/messaging/xnet/v1/mixed_hash_tree.proto)

`get_certified_latest_version` returns a protobuf `CertifiedResponse`. Its
mixed hash tree commits to a canonical unsigned-LEB128 `current_version` leaf
and the pruned Registry delta-map root. `get_certified_changes_since` returns
the same certified current version plus a requested range from the delta map.
Neither method directly certifies an arbitrary `get_value` response.

## Trust And Failure Model

The built-in mainnet path trusts only the compiled-in mainnet root key and the
Registry canister identity. It must reject:

- invalid certificate signatures, delegation, or canister authority;
- stale certificates or certificate times outside the caller observation
  window;
- a certificate whose `certified_data` value does not match the mixed-tree
  digest;
- malformed, missing, excessively deep, or excessively large tree nodes;
- pruned digests that are not exactly SHA-256 length;
- absent, unknown, non-leaf, overflowing, truncated, trailing, or
  noncanonical version values;
- delta gaps, regressions, duplicate versions, conflicting mutations, and
  truncated replay presented as completion; and
- a bootstrap or incremental sequence exceeding its explicit call, byte,
  version, key, or value ceilings.

Certificate verification authenticates evidence; it does not make sequential
queries point-in-time atomic. Every reconstructed snapshot identifies its
selected certified Registry version and rejects values newer than it.

## 0.30.0 — Certified Latest Version

The existing `icq nns registry version` command and public report are hard-cut
to the Registry's `get_certified_latest_version` method. The live adapter:

1. rejects non-mainnet network identity before agent construction;
2. performs one response-bounded Registry query;
3. decodes the official protobuf `CertifiedResponse` and mixed hash tree;
4. authenticates the CBOR certificate against the mainnet root key;
5. verifies the Registry canister `certified_data` commitment;
6. reads a canonical unsigned-LEB128 `current_version` leaf;
7. checks certificate time within five minutes of the caller-supplied
   collection time; and
8. returns certificate time, root-key digest, raw certificate, raw encoded
   witness, and exact byte counts.

The report schema moves from version 1 to version 2. Text remains compact and
shows assurance, time, digest, and evidence sizes; JSON preserves raw evidence.
The operation remains live and uncached. Command names and options do not
change.

The mixed-tree decoder currently accepts at most 128 levels and 65,536 nodes,
in addition to the shared 8 MiB native-agent response-body limit. These are
defence-in-depth ceilings rather than an estimate that the latest-version tree
will approach them.

`nns-host` now has a direct CBOR dependency for certificate decoding. The
focused `nns-topology-host` and `subnet-catalog-host` graphs remain unchanged
until certified catalog collection is actually exposed through them.

## 0.30.1 — Certified Delta Batch

This stage adds a pure validator plus a caller-runtime async transport for
one `get_certified_changes_since` batch. A validated batch must retain:

- requested start version;
- certified latest version;
- first and last visible delta versions;
- canonical ordered mutations and mutation timestamps;
- certificate time, root-key digest, endpoint, and raw evidence sizes;
- whether more certified versions remain; and
- exact call and byte accounting.

Visible delta labels are eight-byte big-endian versions. They must begin at
`requested_version + 1`, increase by exactly one, and never exceed the
certified latest version. Each leaf must decode as the official
`HighCapacityRegistryAtomicMutateRequest`. Large-value chunk references are
not accepted as complete values until every referenced chunk is retrieved and
its SHA-256 digest verified under explicit additional bounds.

A batch validator does not publish a catalog and does not expose
`CatalogAssurance::Certified`.

The public operation performs exactly one query and never follows
`more_available` implicitly. The caller must issue the next request from the
returned last version. The validator enforces at most 1,000 visible versions,
65,536 mutations, 65,536 preconditions, 4,096 bytes per key, 2 MiB of combined
inline values, the shared 8 MiB agent response limit, and the existing
mixed-tree depth and node limits. These ceilings are returned in the report so
custom sources and consumers can audit the applied contract.

The report preserves raw mutation discriminants and typed native
insert/update/delete/upsert kinds, key and inline-value bytes as canonical
lowercase hexadecimal, atomic mutation order, preconditions, timestamps,
query and byte counts, and certificate evidence. Unknown mutation kinds,
duplicate keys in one atomic request, invalid delete/value combinations,
noncontiguous version labels, and incomplete large-value chunk references fail
closed. A pure public validator recomputes every structural derived count and
boundary for trusted custom source reports. It checks certificate evidence
shape and freshness but does not reauthenticate custom-source certificate
bytes; cryptographic authentication remains that source's responsibility.

This operation is mainnet-only, live, async, and uncached. It does not loop,
bootstrap historical state, retrieve large-value chunks, replay mutations,
publish a mirror, alter CLI grammar, or strengthen Subnet Catalog assurance.

## Planned Mirror And Catalog Projection

A certified mirror, if accepted after measurement, uses a separate versioned
cache identity from ordinary Subnet Catalog evidence. Bootstrap and
incremental refresh are explicit operations; an ordinary catalog load must
never begin an unbounded historical download.

Publication requires all of:

1. a contiguous replay from an accepted bootstrap anchor through the selected
   certified latest version;
2. deterministic application of insert, update, upsert, and delete mutations;
3. complete reconstruction of every Registry key needed by the Subnet Catalog;
4. projection through the existing raw Subnet-kind, classification, routing,
   canonical-ordering, digest, and validated-authority path;
5. certificate and root-key provenance attached to the resulting catalog; and
6. one atomic cache replacement under a dedicated refresh lock.

The implementation must measure current mainnet history before fixing default
ceilings. If a safe bootstrap cannot be bounded in calls, bytes, time, and
storage, `CatalogAssurance::Certified` remains unsupported. The existing
`UncertifiedQuery` and explicit `MultiEndpointAgreement` paths continue
unchanged.

## Cache And Compatibility

The certified latest-version and single-delta-batch reports create no cache.
Future mirror content must not share a file with version-2 ordinary Subnet
Catalog caches, and no automatic migration or fallback reader is added. Before
1.0, any replacement schema is a hard cut.

Failed certified refreshes must preserve the last complete certified mirror.
Cache-only, refresh, refresh-missing, and refresh-stale operations remain
distinct. A caller's minimum assurance policy may reject weaker evidence but
must never silently trigger a different network or source selection.

## Acceptance Criteria

- The live Registry version path makes exactly one certified method call.
- The live delta-batch path makes exactly one certified method call and returns
  `more_available` without an implicit follow-up.
- Certificate signature, delegation, time, canister identity, certified-data
  commitment, tree structure, digest sizes, and canonical version encoding are
  validated before a version is returned.
- Fixture sources cannot mark malformed evidence as a valid version report.
- Text does not print full certificate or witness hex; JSON preserves both.
- `CatalogAssurance::Certified` remains rejected until complete certified
  replay and projection exist.
- No certified operation hides an unbounded bootstrap, pagination loop, or
  large-value follow-up.
- Existing exact-version joins, endpoint agreement, cache paths, cache policy,
  CLI grammar, and process-output boundaries remain intact.
- Focused no-default, `nns-host`, `host`, public-API, Clippy, documentation,
  and formatting checks pass.
