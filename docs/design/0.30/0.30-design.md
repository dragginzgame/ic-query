# 0.30 Certified Registry Evidence

## Status

- State: `0.30.8` certified latest-version, complete-value delta batches,
  bounded replay, exact-target sessions, explicit async bootstrap, and bounded
  sizing probes verified across complete measured mainnet history, with compact
  replay provenance commitments; persistence and catalog publication remain
  planned
- Last reviewed: 2026-08-06
- Scope: bounded authenticated Registry evidence without overstating ordinary
  query assurance
- CLI grammar: unchanged

## Goal

`0.30` establishes a cryptographically authenticated path from the mainnet IC
root key to Registry evidence. The work proceeds in independently useful
stages: first authenticate the Registry's latest version, then validate
certified delta batches, then reconstruct and publish a certified Subnet
Catalog only if bootstrap and incremental replay remain explicitly bounded.

The release must preserve the distinction between:

- a certified `current_version` leaf;
- an exact-version ordinary `get_value` join;
- matching ordinary evidence from multiple endpoints; and
- Registry key state reconstructed from a complete certified delta sequence.

Only the final case may produce `CatalogAssurance::Certified`.

## Upstream Contract

The implementation follows the pinned Registry canister implementation and
protobuf definitions reviewed for this design:

- [Registry certified query methods](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/canister/canister/canister.rs)
- [Registry certification tree](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/canister/src/certification.rs)
- [Registry transport protobuf](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/transport/proto/ic_registry_transport/pb/v1/transport.proto)
- [Registry chunk storage](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/registry/canister/src/storage.rs)
- [Upstream chunk reconstruction contract](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/nervous_system/chunks/src/lib.rs)
- [Mixed hash-tree protobuf](https://github.com/dfinity/ic/blob/eebffee61e857f28e47fc4038a8b3309f2674abf/rs/protobuf/def/messaging/xnet/v1/mixed_hash_tree.proto)

`get_certified_latest_version` returns a protobuf `CertifiedResponse`. Its
mixed hash tree commits to a canonical unsigned-LEB128 `current_version` leaf
and the pruned Registry delta-map root. `get_certified_changes_since` returns
the same certified current version plus a requested range from the delta map.
Neither method directly certifies an arbitrary `get_value` response.

## Trust And Failure Model

The built-in mainnet path trusts only the compiled-in mainnet root key and the
Registry canister identity. It must reject:

- invalid certificate signatures, delegation, or canister authority;
- stale certificates or certificate times outside the caller observation
  window;
- a certificate whose `certified_data` value does not match the mixed-tree
  digest;
- malformed, missing, excessively deep, or excessively large tree nodes;
- pruned digests that are not exactly SHA-256 length;
- absent, unknown, non-leaf, overflowing, truncated, trailing, or
  noncanonical version values;
- delta gaps, regressions, duplicate versions, noncanonical mutation order,
  and truncated replay presented as completion; and
- a bootstrap or incremental sequence exceeding its explicit call, byte,
  version, key, or value ceilings.

Certificate verification authenticates evidence; it does not make sequential
queries point-in-time atomic. Every reconstructed snapshot identifies its
selected certified Registry version and rejects values newer than it.

## 0.30.0 — Certified Latest Version

The existing `icq nns registry version` command and public report are hard-cut
to the Registry's `get_certified_latest_version` method. The live adapter:

1. rejects non-mainnet network identity before agent construction;
2. performs one response-bounded Registry query;
3. decodes the official protobuf `CertifiedResponse` and mixed hash tree;
4. authenticates the CBOR certificate against the mainnet root key;
5. verifies the Registry canister `certified_data` commitment;
6. reads a canonical unsigned-LEB128 `current_version` leaf;
7. checks certificate time within five minutes of the caller-supplied
   collection time; and
8. returns certificate time, root-key digest, raw certificate, raw encoded
   witness, and exact byte counts.

The report schema moves from version 1 to version 2. Text remains compact and
shows assurance, time, digest, and evidence sizes; JSON preserves raw evidence.
The operation remains live and uncached. Command names and options do not
change.

The mixed-tree decoder currently accepts at most 128 levels and 65,536 nodes,
in addition to the shared 8 MiB native-agent response-body limit. These are
defence-in-depth ceilings rather than an estimate that the latest-version tree
will approach them.

`nns-host` now has a direct CBOR dependency for certificate decoding. The
focused `nns-topology-host` and `subnet-catalog-host` graphs remain unchanged
until certified catalog collection is actually exposed through them.

## 0.30.1 — Certified Delta Batch

This stage adds a pure validator plus a caller-runtime async transport for
one `get_certified_changes_since` batch. A validated batch must retain:

- requested start version;
- certified latest version;
- first and last visible delta versions;
- canonical ordered mutations and mutation timestamps;
- certificate time, root-key digest, endpoint, and raw evidence sizes;
- whether more certified versions remain; and
- exact call and byte accounting.

Visible delta labels are eight-byte big-endian versions. They must begin at
`requested_version + 1`, increase by exactly one, and never exceed the
certified latest version. Each leaf must decode as the official
`HighCapacityRegistryAtomicMutateRequest`. In `0.30.1`, every large-value
chunk reference was rejected as incomplete pending a bounded retrieval design.

A batch validator does not publish a catalog and does not expose
`CatalogAssurance::Certified`.

The `0.30.1` public operation performs exactly one query and never follows
`more_available` implicitly. The caller must issue the next request from the
returned last version. The validator enforces at most 1,000 visible versions,
65,536 mutations, 65,536 preconditions, 4,096 bytes per key, 2 MiB of combined
inline values, the shared 8 MiB agent response limit, and the existing
mixed-tree depth and node limits. These ceilings are returned in the report so
custom sources and consumers can audit the applied contract.

The report preserves raw mutation discriminants and typed native
insert/update/delete/upsert kinds, key and inline-value bytes as canonical
lowercase hexadecimal, atomic mutation order, preconditions, timestamps,
query and byte counts, and certificate evidence. Unknown mutation kinds,
decreasing key order, noncontiguous version labels, and initially unsupported
large-value chunk references fail closed. Repeated committed keys and retained
delete content are handled by the later `0.30.7` compatibility stage. A
pure public validator recomputes every structural derived count and
boundary for trusted custom source reports. It checks certificate evidence
shape and freshness but does not reauthenticate custom-source certificate
bytes; cryptographic authentication remains that source's responsibility.

The `0.30.1` operation is mainnet-only, live, async, and uncached. It does not
loop, bootstrap historical state, retrieve large-value chunks, replay
mutations, publish a mirror, alter CLI grammar, or strengthen Subnet Catalog
assurance.

## 0.30.2 — Bounded Large-Value Completion

The certified delta transport now completes every
`LargeValueChunkKeys` mutation before returning the batch. The certified tree
authenticates the ordered SHA-256 chunk references; each content-addressed
`get_chunk` response is accepted only when its content hashes to the expected
digest. Repeated hashes within or across mutations reuse the already verified
content rather than issuing another query.

Completion is one finite extension of the selected delta response, not hidden
delta pagination. The transport enforces all of these fixed ceilings:

- 64 chunk references across the batch;
- 1,800,000 decoded bytes per chunk;
- 10 MiB reconstructed bytes per value;
- 16 MiB combined inline and reconstructed value bytes;
- 32 MiB of encoded chunk-response bytes; and
- the shared 8 MiB limit on each individual agent response body.

The report schema moves from version 1 to version 2. Every mutation records
whether its original certified representation was absent, inline, or chunked;
chunked rows retain the ordered digest list and the complete reconstructed
value. Batch evidence separately reports certified-response bytes,
chunk-response bytes, chunk references, unique chunk query calls, inline
value bytes, reconstructed value bytes, and their totals. The pure validator
recomputes all structural counts and requires the chunk-query count to equal
the number of unique retained digests.

The same bounded reconstruction helper now protects ordinary Registry
`get_value` large-value responses used by exact-version catalog and topology
collectors. That path still provides ordinary query evidence, not certified
assurance. This slice adds no cache, replay loop, CLI surface, or
`CatalogAssurance::Certified` path.

## 0.30.3 — Pure Bounded Replay State

This stage adds an in-memory replay state and one-batch atomic apply function.
The state always starts empty immediately before Registry version one. A batch
is accepted only after the existing public certified-delta validator succeeds
and its `requested_version` exactly equals the state's current
`through_version`.

Replay follows the pinned Registry's committed-changelog reconstruction
semantics, not the validation rules for a proposed new transaction. The
Registry stably sorts committed rows by key and normalizes insert, update, and
upsert operations to replacement writes before recording the certified
changelog. Replay therefore treats every committed non-delete row as
replacement and every delete as removal. Repeated same-key rows remain in
their stable order and are applied sequentially. Recorded preconditions and
delete value content are retained in batch evidence but are not re-evaluated
or applied after the transaction has already been committed.

Every apply requires caller-selected maximum live entries and maximum combined
raw key/value bytes. There is deliberately no default memory budget. The
existing batch ceilings still bound the amount of new content decoded by one
call. Application occurs on a candidate state; version mismatch, invalid batch
evidence, accounting failure, or a caller ceiling leaves the original state
unchanged.

`NnsRegistryReplayState` retains canonical raw-byte key order, current raw
values, each value's last mutation version and timestamp, total content bytes,
and the version through which replay has completed. Progress reports whether
that state reached the current batch's certified latest version. The state is
not serializable authority evidence and does not carry certificates; callers
must retain the validated batch reports that produced it.

This slice performs no network call, follows no cursor, chooses no bootstrap
budget, writes no cache, exposes no CLI, and does not enable
`CatalogAssurance::Certified`.

## 0.30.4 — Exact-Target Replay Session

This stage adds pure cumulative coordination around the one-batch replay
primitive. The first accepted report selects its certified latest Registry
version as the immutable session target. A later report may authenticate a
newer live latest version, but the session applies only contiguous mutations
through its original target. A later report that no longer certifies at least
the target fails closed.

One session requires explicit ceilings for the selected Registry version,
admitted batch count, reported query calls, reported encoded response bytes,
live state entries, and combined raw key/value bytes. It retains cumulative
accepted batch, call, response-byte, and applied-mutation accounting. All
checks happen before session counters are published, and the underlying batch
application remains atomic, so any validation, target, root-key, cumulative,
or state-limit error leaves the session unchanged.

Every admitted report must retain the same root-key digest. Sources may differ
because endpoint identity is not the cryptographic authority, but every report
still validates against its explicit request endpoint and mainnet Registry
identity. The public custom-source boundary continues to make authentication
the source's responsibility.

The session deliberately does not fetch a batch or follow `more_available`.
Its cumulative ceilings bound evidence admitted after the caller has obtained
it; they do not reserve or constrain network work already performed by that
caller. A future live bootstrap coordinator needs its own pre-call budget and
mainnet measurements before any default ceiling is selected.

Session state remains nonserializable and is not standalone authority. This
slice adds no cache, CLI, catalog projection, assurance promotion, or implicit
source call.

## 0.30.5 — Explicit Bounded Bootstrap

This stage adds a caller-runtime async coordinator that explicitly bootstraps
from Registry version zero. It creates each next delta request from the replay
session's current version, uses the first response to pin the immutable target,
and returns only when that exact version is reconstructed. Newer versions
observed during later calls remain validated but are not applied beyond the
target.

Before invoking the built-in source, the coordinator proves that the remaining
session budget can accommodate one complete worst-case batch under the fixed
delta contract. The reservation is:

- one certified `get_certified_changes_since` query;
- up to 64 distinct `get_chunk` queries;
- up to 8 MiB for the certified response body; and
- up to 32 MiB across encoded chunk responses.

Therefore every attempted batch reserves 65 calls and 40 MiB before any call.
After a successful report, cumulative accounting advances by actual calls and
bytes, so unused reserved capacity remains available to later batches. If the
remaining budget cannot cover another full attempt, collection stops without
starting that source call. A failed in-flight source call was already covered
by its reservation and terminates the operation.

The network contract is enforced before reservation or source invocation. The
built-in live path authenticates every response and stays within the one-batch
transport ceilings. The custom-source variant is useful for fixtures and
specialized authenticated transports, but such a source remains responsible
for bounding its own internal work; the coordinator can validate and account
only what it returns.

There are deliberately no default bootstrap limits. The operation name and
request make its multi-call behavior explicit, it uses the caller's runtime
and cancellation, and it writes no cache. An error discards the coordinator's
owned partial session rather than exposing incomplete state as a successful
bootstrap.

This slice still does not retain a persistable certificate chain, publish a
mirror, project a Subnet Catalog, or enable `CatalogAssurance::Certified`.
Current mainnet history must be measured before any recommended or default
bootstrap budget is documented.

## 0.30.6 — Bounded Bootstrap Probe

The complete bootstrap intentionally discards its owned partial session on an
error. That is the correct publication contract but makes empirical sizing
needlessly opaque. This stage adds a separate diagnostic probe that shares the
same collection loop and can terminate successfully with one of two explicit
statuses:

- `Complete` means the first response's exact certified target was fully
  reconstructed; or
- `CapacityReached` means another worst-case batch would exceed a named batch,
  query-call, or response-byte ceiling. It reports the configured maximum and
  cumulative amount required for the rejected attempt.

The capacity status is decided before source invocation, so the outcome retains
the state and actual accounting from admitted batches without performing the
call that would exceed its budget. A zero-batch budget returns an empty
`CapacityReached` outcome and performs no source work. Unsupported networks,
source failures, malformed evidence, replay failures, and state payload limits
remain errors and never masquerade as normal probe completion.

Complete bootstrap delegates to this same loop, accepts only `Complete`, and
converts `CapacityReached` back into `SessionLimitExceeded`. This preserves its
complete-only contract and prevents the diagnostic API from weakening normal
bootstrap semantics.

Probe state is deliberately in-memory and nonserializable. An incomplete probe
is sizing evidence, not a resumable checkpoint, cache candidate, certified
mirror, or Subnet Catalog authority. No CLI is added, and no recommended or
default mainnet limits are selected by this slice.

Historical Registry entries also establish a wire-compatibility requirement.
The legacy `RegistryMutation.value` was a plain proto3 `bytes` field, so an
empty value was omitted from the encoded mutation. When that historical byte
sequence is decoded through `HighCapacityRegistryMutation`, its content oneof
is therefore absent. The official Registry transport interprets absent
content on a non-delete mutation as an empty value; ic-query must do the same.
Absent content on a delete remains a delete. The later complete-history probe
showed that some committed deletes retain ignored content; `0.30.7` preserves
that evidence without applying it.

A bounded mainnet observation on 2026-08-06 authenticated exact target
`62948` and reconstructed versions `1..=270` in one call: 1,082 applied
mutations, 804 current entries, and 1,386,570 encoded response bytes. The
one-batch probe then stopped before another call with `CapacityReached`. This
is evidence that the diagnostic boundary works; it is not a complete-history
budget recommendation.

## 0.30.7 — Complete-History Compatibility And Measurement

A larger bounded probe exposed two more differences between transaction-input
validation and the Registry's committed changelog. First, one atomic version
may contain the same key repeatedly. The canister uses a stable key sort and
then applies every row sequentially, so equal-key ordering is significant and
the final row determines current state. Validation now requires nondecreasing
raw key order rather than uniqueness, preserves every row, and rejects only a
decrease.

Second, historical committed deletes may retain value content. The canister
ignores that content and records a deletion marker when reconstructing current
state. ic-query retains the certified content, encoding, and byte accounting
as evidence but replay removes the key. These rules apply only to interpreting
already committed certified history; ic-query does not submit mutations.

After both corrections, a cacheless bounded probe completely reconstructed
exact mainnet Registry target `62948` from version zero. The run used 75
batches and 77 calls, admitted 63,814,080 encoded response bytes, applied
147,284 mutations, and produced 17,184 current keys occupying 22,345,176 raw
key/value bytes. Its explicit ceilings were 128 batches, 8,320 calls, 256 MiB
of responses, 100,000 keys, and 128 MiB of state.

This single observation establishes practical feasibility and validates the
complete replay path. It does not establish defaults, a service-level budget,
or a certified cache authority contract. Persistence and catalog promotion
remain separate stages.

## 0.30.8 — Replay Provenance Commitments

Projection needs compact, deterministic correlation evidence before it needs
a filesystem format. `NnsRegistryReplaySession` therefore retains provenance
without adding a parallel receipt DTO. Each successfully admitted report
advances a domain-separated SHA-256 chain over its complete deterministic JSON
encoding and the prior chain digest. Encoding streams directly into the hash,
so the session does not allocate another report-sized buffer.

The session also retains distinct source endpoint strings in canonical order
and the minimum and maximum certificate times present in admitted reports.
Custom source reports have already passed structural validation, but their
source remains responsible for endpoint validity and cryptographic
authentication; the session does not upgrade that trust boundary. One public
provenance-schema constant versions both digest contracts.

Once the pinned exact target is complete, a separate domain-separated state
digest commits to the target version, entry and content-byte accounting,
canonical raw keys and values, and each value's last mutation version and
timestamp. It remains absent for empty or partial sessions. Completion is
measured against the pinned target, not a newer latest version that a later
report may observe.

All candidate provenance is computed before or alongside candidate replay and
published only after the batch applies successfully. A cumulative-limit,
validation, root-key, encoding, or state-limit failure leaves the prior state,
counters, endpoints, times, and digests unchanged.

These digests are commitments, not certificate chains or standalone proofs.
They are in-memory and nonserializable in this stage. No cache, catalog
projection, assurance promotion, new source call, or CLI surface is added.

## Planned Mirror And Catalog Projection

A certified mirror, if accepted after measurement, uses a separate versioned
cache identity from ordinary Subnet Catalog evidence. Bootstrap and
incremental refresh are explicit operations; an ordinary catalog load must
never begin an unbounded historical download.

Publication requires all of:

1. a contiguous replay from an accepted bootstrap anchor through the selected
   certified latest version;
2. deterministic application of insert, update, upsert, and delete mutations;
3. complete reconstruction of every Registry key needed by the Subnet Catalog;
4. projection through the existing raw Subnet-kind, classification, routing,
   canonical-ordering, digest, and validated-authority path;
5. certificate and root-key provenance attached to the resulting catalog; and
6. one atomic cache replacement under a dedicated refresh lock.

The implementation must measure current mainnet history before fixing default
ceilings. If a safe bootstrap cannot be bounded in calls, bytes, time, and
storage, `CatalogAssurance::Certified` remains unsupported. The existing
`UncertifiedQuery` and explicit `MultiEndpointAgreement` paths continue
unchanged.

## Cache And Compatibility

The certified latest-version, single-delta-batch, and bootstrap operations
create no cache.
Future mirror content must not share a file with version-2 ordinary Subnet
Catalog caches, and no automatic migration or fallback reader is added. Before
1.0, any replacement schema is a hard cut.

Failed certified refreshes must preserve the last complete certified mirror.
Cache-only, refresh, refresh-missing, and refresh-stale operations remain
distinct. A caller's minimum assurance policy may reject weaker evidence but
must never silently trigger a different network or source selection.

## Acceptance Criteria

- The live Registry version path makes exactly one certified method call.
- The live delta-batch path makes exactly one certified method call, completes
  only that batch's bounded chunk references, and returns `more_available`
  without an implicit delta-batch follow-up.
- Certificate signature, delegation, time, canister identity, certified-data
  commitment, tree structure, digest sizes, and canonical version encoding are
  validated before a version is returned.
- Fixture sources cannot mark malformed evidence as a valid version report.
- Pure replay accepts only the next validated batch, applies committed rows
  atomically, and preserves the prior state on a caller-limit failure.
- Pure replay sessions pin one exact first-batch target, reject root-key or
  target regression, and do not apply later-observed versions beyond it.
- Explicit bootstrap rejects non-mainnet before source work, reserves one
  maximum-size batch before every built-in call, and returns only complete
  exact-target state.
- Diagnostic probes return typed complete or pre-call capacity status while
  keeping incomplete sessions outside every cache and authority path.
- Committed same-key mutations retain stable order, and retained delete
  content is preserved as evidence but ignored by replay.
- Replay provenance commitments advance atomically, and the canonical state
  digest remains absent until the pinned target is complete.
- Text does not print full certificate or witness hex; JSON preserves both.
- `CatalogAssurance::Certified` remains rejected until complete certified
  replay and projection exist.
- No certified operation hides an unbounded bootstrap, pagination loop, or
  large-value follow-up; every chunk call and byte is bounded and reported.
- Existing exact-version joins, endpoint agreement, cache paths, cache policy,
  CLI grammar, and process-output boundaries remain intact.
- Focused no-default, `nns-host`, `host`, public-API, Clippy, documentation,
  and formatting checks pass.
